# RingCentral inbound-call screen-pop connector specification

- **Status:** Planned; specification only
- **Product:** Intelligent Sales / Intelligent CRM
- **Provider:** RingCentral RingEX
- **Last verified:** 2026-08-25

This document specifies a per-user RingCentral connection that alerts an authenticated
Intelligent Sales user when an inbound call is ringing, matches the caller ID to CRM records, and
offers to open the best Account, Opportunity, or Lead record. It does not answer or control calls.

The declarative RingCentral REST connector already exists in
[`swarm-apps/connectors/ringcentral.yaml`](../../swarm-apps/connectors/ringcentral.yaml). This
document covers the interactive OAuth, realtime notification, and CRM screen-pop behavior that a
declarative REST resource cannot express.

## Decision summary

| Concern | Decision |
| --- | --- |
| User authentication | RingCentral 3-legged OAuth Authorization Code with PKCE (S256) |
| End-user action | **Connect RingCentral** button inside Intelligent Sales |
| Production redirect URI | `https://gsquared.oshal.ai/api/connect/ringcentral/callback` |
| Local redirect URI | `http://localhost:35457/api/connect/ringcentral/callback` |
| Realtime transport | One server-owned RingCentral WebSocket per connected user who currently has the CRM open |
| RingCentral event filter | `/restapi/v1.0/account/~/extension/~/presence?detailedTelephonyState=true` |
| RingCentral scopes | `ReadPresence`, `WebSocketsSubscription` |
| CRM browser transport | Authenticated, owner-scoped Server-Sent Events (SSE) |
| Match key | Normalized inbound caller number against `phone` and `phone_alt` |
| Duplicate key | Authenticated user plus `telephonySessionId` |
| Call handling | Notification and navigation only; no answering, dialing, recording, or call control |

## Purpose

When a rep has Intelligent Sales open and a RingCentral call begins ringing for that rep:

1. RingCentral pushes the presence change to the OSHAL API over an outbound WebSocket.
2. The API forwards a minimized, user-scoped ringing event to that rep's CRM browser over SSE.
3. Intelligent Sales matches the inbound number to visible CRM business partners.
4. The UI shows a non-blocking prompt with the best Account, Opportunity, or Lead destination.
5. The user chooses whether to open a record. The integration never answers the call.

### Non-goals for v1

- Answering, rejecting, holding, transferring, or otherwise controlling calls.
- Embedding a RingCentral softphone.
- Placing outbound calls or click-to-dial.
- Recording, transcribing, or analyzing call audio.
- Reading call history, messages, voicemail, or SMS.
- Receiving RingCentral events while the user has no Intelligent Sales browser session open.
- Using a shared admin/service user, password grant, or a JWT generated by each user.
- Automatically creating a lead or navigating away without the user's choice.

## Current repository state

The following pieces already exist:

- The read-only RingCentral REST connector and its conformance test:
  [`ringcentral.yaml`](../../swarm-apps/connectors/ringcentral.yaml) and
  [`ringcentral-spec.spec.ts`](../../tests/unit/connectors/ringcentral-spec.spec.ts).
- Generic per-user OAuth start/callback routes under `/api/connect`.
- Encrypted, owner-scoped access/refresh-token storage in `oshal_connections`.
- PKCE verifier generation and signed OAuth state primitives.
- Intelligent Sales phone normalization and indexed matching against `phone` and `phone_alt`.
- An authenticated Intelligent Sales application mounted at `/api/intelligent-sales`.

The following pieces are not implemented yet:

- `ringcentral` is not registered in the runtime OAuth provider registry, so
  `/api/connect/ringcentral/start` and `/api/connect/ringcentral/callback` are not live today.
- RingCentral credentials and redirect settings are not passed through the deployment config.
- There is no per-user RingCentral WebSocket manager or RingCentral-to-browser SSE route.
- Intelligent Sales has no dedicated inbound-phone match endpoint or screen-pop component.
- The existing generic callback returns to `/utilities`; popup completion and return-to-CRM
  behavior must be added.

The production callback URI below is therefore the route to implement and register, not a claim
that the callback is currently operational.

## User experience

### Connection states

The CRM header or integration panel must expose one of these states:

| State | UI |
| --- | --- |
| Not configured by operator | Disabled button: **RingCentral needs administrator setup** |
| Not connected | **Connect RingCentral** |
| Connecting | Spinner: **Connecting to RingCentral...** |
| Connected and listener active | Green indicator: **RingCentral connected — listening** |
| Connected but reconnecting | Amber indicator: **RingCentral reconnecting...** |
| Authorization expired/revoked | **Reconnect RingCentral** |
| Connected but CRM inactive | **Connected — listener starts when this CRM is open** |

### Connect flow

```text
Intelligent Sales browser
  -> GET /api/connect/ringcentral/start?mode=popup&returnTo=<CRM path>
  -> RingCentral-hosted login, SSO/MFA, and consent
  -> GET /api/connect/ringcentral/callback?code=...&state=...
  -> API exchanges the one-time code and stores encrypted per-user tokens
  -> callback notifies the opener and closes
  -> CRM opens its owner-scoped event stream
  -> API starts that user's RingCentral WebSocket subscription
```

The popup is user-initiated so normal popup blockers permit it. RingCentral's authorization
request may use `display=popup`. If the popup cannot open, the UI must fall back to a full-page
redirect and return the user to Intelligent Sales after authorization.

The popup callback must return fixed application-controlled HTML that:

1. calls `window.opener.postMessage` with only a success/error code and provider id;
2. specifies the exact initiating origin, never `*`;
3. contains no access token, refresh token, authorization code, or caller data; and
4. closes itself. If there is no opener, it performs a safe same-origin redirect to the CRM.

The opener must verify `event.origin`, `event.source`, the provider id, and the expected pending
connection attempt before accepting the message.

## RingCentral application registration

Create a dedicated **REST API App** in the RingCentral Developer Console with these settings:

| Console setting | Required value |
| --- | --- |
| Authentication | **3-legged OAuth flow authorization code** |
| Application platform | **Server-side web app** |
| PKCE | Use S256 on every authorization attempt |
| Issue refresh tokens | **Yes** |
| Application access | **Private** for the current same-RingCentral-organization deployment |
| Scopes | `ReadPresence`, `WebSocketsSubscription` |
| Production redirect | `https://gsquared.oshal.ai/api/connect/ringcentral/callback` |

Use a public RingCentral app only if Intelligent Sales will be sold to organizations with unrelated
RingCentral accounts. Public apps accept users from other accounts and are subject to additional
RingCentral review. A private app is correct while all connecting users belong to the organization
that owns this RingCentral app.

Do not request `CallControl`, `ReadCallLog`, messaging, recording, or account-wide admin scopes for
this feature. Permissions granted to the app and permissions assigned to the individual RingCentral
user both apply.

### Redirect URI

Register this exact production value, with no trailing slash:

```text
https://gsquared.oshal.ai/api/connect/ringcentral/callback
```

The production environment must set the same value explicitly:

```dotenv
RINGCENTRAL_REDIRECT_URI=https://gsquared.oshal.ai/api/connect/ringcentral/callback
```

This override is required because the current repository-wide `APP_URL` is
`https://oshal.agenticfederal.us`, while Intelligent Sales is served at `gsquared.oshal.ai`.
Starting and completing the OAuth ceremony on the CRM host preserves the correct browser session
and PKCE cookie. The URI sent in both the authorization request and token exchange must match the
registered URI character-for-character.

For local development, use a separate development registration or an additional registered URI:

```text
http://localhost:35457/api/connect/ringcentral/callback
```

Local code must override `RINGCENTRAL_REDIRECT_URI` to that localhost value. Production and
RingCentral's `devtest` sandbox have separate credentials and API hosts; tokens from one environment
must never be sent to the other.

### Environment variables

Store the operator-owned app credentials in the gitignored root file
`C:\Projects\oshal\.env`:

```dotenv
RINGCENTRAL_CLIENT_ID=
RINGCENTRAL_CLIENT_SECRET=
RINGCENTRAL_REDIRECT_URI=https://gsquared.oshal.ai/api/connect/ringcentral/callback
RINGCENTRAL_SERVER_URL=https://platform.ringcentral.com
```

The RingCentral `credentials.json` download is not required by this design. If it is downloaded,
keep it outside the repository and use it only as a source for the Client ID and Client Secret
values above; do not commit or mount the whole file.

Real values belong only in the operator secret store or `.env`; they must never be committed,
logged, returned to the browser, added to a model prompt, or passed to package code. Deployment
manifests must pass these variables only to the API process that owns the OAuth and WebSocket
operations.

Adding these variables today only stages the credentials. The current runtime and compose files do
not yet register/pass the RingCentral values, so the connection button will not work until the
implementation items in this specification are completed.

## OAuth contract

### Authorization request

The start route constructs a RingCentral authorization URL at:

```text
https://platform.ringcentral.com/restapi/oauth/authorize
```

Required parameters:

```text
response_type=code
client_id=<configured client id>
redirect_uri=https://gsquared.oshal.ai/api/connect/ringcentral/callback
state=<signed, short-lived correlation value>
code_challenge=<base64url SHA-256 challenge>
code_challenge_method=S256
display=popup
```

The signed state must bind at least:

- connector id `ringcentral`;
- initiating OSHAL user `sub`;
- issued-at/expiry (ten minutes maximum);
- random single-use attempt identifier;
- popup versus redirect completion mode; and
- a sanitized same-origin return path.

The PKCE verifier must be high entropy, encrypted in an `HttpOnly`, `Secure`, `SameSite=Lax`,
short-lived cookie or stored in a server-side one-time record bound to the attempt. State and PKCE
must both be verified before exchanging the code. A callback is invalid after first successful use.

### Callback and account identity

The callback must:

1. require an authenticated OSHAL user;
2. verify signed state, expiry, provider, attempt, and exact user binding;
3. verify the PKCE code verifier;
4. exchange the authorization code using RingCentral's documented PKCE contract or official SDK;
5. persist the returned access token, rotated refresh token, expiry values, scopes, and
   RingCentral `owner_id` in the encrypted per-user connection store;
6. fetch `/restapi/v1.0/account/~/extension/~` to obtain a human-readable account/extension label;
7. delete the one-time state/verifier material; and
8. complete the popup or safe redirect without exposing tokens.

RingCentral has provider-specific token-exchange and refresh behavior. The implementation must use
a RingCentral-specific adapter or the official RingCentral JavaScript SDK instead of assuming the
generic provider exchange is compatible.

### Token lifecycle

- The browser receives only the OSHAL session cookie; RingCentral tokens stay server-side.
- Access and refresh tokens use the existing per-user envelope encryption in
  `oshal_connections`.
- Use the returned `expires_in` and `refresh_token_expires_in`; do not hard-code token lifetimes.
- Refresh before an access token expires and before requesting/recovering a WebSocket session.
- RingCentral refresh tokens rotate. Refresh must be serialized per connection so two workers or
  reconnect attempts cannot spend the same refresh token concurrently.
- Persist the new access token, refresh token, and expirations atomically before exposing them to
  another caller.
- An invalid/revoked refresh token transitions the connection to **Reconnect required**; it must
  not create an infinite refresh loop.
- Disconnect revokes the RingCentral authorization when supported, closes the WebSocket, removes
  the encrypted connection, clears dedupe state, and updates all open CRM tabs.

## Realtime listener

### Ownership and lifecycle

The OSHAL API owns all RingCentral WebSocket connections. RingCentral tokens and WebSocket tokens
must never enter browser JavaScript or the Intelligent Sales package.

The CRM opens an authenticated owner-scoped stream:

```text
GET /api/connect/ringcentral/events
Accept: text/event-stream
```

Behavior:

- The first active CRM stream for a user acquires one RingCentral listener for that user's selected
  RingCentral connection.
- Additional tabs for the same user share that listener.
- The listener is keyed by OSHAL `user_sub` and RingCentral connection id; events may only be
  delivered to SSE clients for that same `user_sub`.
- Closing the last CRM stream releases the listener after a short grace period to absorb page
  reloads. v1 does not listen indefinitely while the CRM is closed.
- A process shutdown closes all RingCentral WebSockets cleanly.
- A future always-on requirement should use a central RingCentral webhook subscription; it is not
  part of v1.

### RingCentral subscription

Use the authenticated user's current extension token (`~` means the authenticated account and
extension) and subscribe to exactly:

```text
/restapi/v1.0/account/~/extension/~/presence?detailedTelephonyState=true
```

Do not use the telephony-sessions event for v1 because that requires `CallControl`; detailed
presence supplies the ringing state and caller number with only `ReadPresence`.

For every notification, inspect all `body.activeCalls` entries and select entries satisfying:

```text
direction == "Inbound"
telephonyStatus == "Ringing"
```

Read only the minimum fields required for the screen-pop:

- `body.extensionId`
- `body.sequence`
- `activeCalls[].telephonySessionId`
- `activeCalls[].partyId` when present
- `activeCalls[].from`
- `activeCalls[].fromName` when present
- `activeCalls[].queueCall`
- `activeCalls[].startTime`

Normalize the event before broadcasting it internally:

```json
{
  "type": "ringcentral.inbound-ringing",
  "telephonySessionId": "opaque-session-id",
  "extensionId": "opaque-extension-id",
  "from": "+15552001000",
  "fromName": "Optional caller name",
  "queueCall": false,
  "startedAt": "2026-08-25T20:15:30.000Z",
  "receivedAt": "2026-08-25T20:15:30.250Z"
}
```

Never include access tokens, WebSocket tokens, account-wide data, call audio, or unrelated active
calls in the browser event.

### Duplicate and reconnect behavior

- Deduplicate on `(user_sub, telephonySessionId)` for at least the lifetime of the ringing call and
  a bounded TTL afterward.
- Repeated presence snapshots update an existing prompt; they do not create another prompt.
- A different `partyId` for the same telephony session may update routing metadata but must not
  duplicate the user's prompt.
- Queue calls are eligible only when the call is actually offered to/ringing for the authenticated
  extension.
- On a transient disconnect, attempt RingCentral session recovery within its supported recovery
  window. If recovery fails, obtain a valid token, reconnect, and resubscribe.
- Respond to WebSocket ping frames, send a RingCentral heartbeat after an appropriate idle period,
  and expect a forced reconnect at least every 24 hours.
- Use bounded exponential backoff with jitter. Authorization failures stop retrying and request
  reauthentication; network/service failures keep retrying while the CRM stream remains active.

## CRM matching and navigation

### Match endpoint

Add an authenticated Intelligent Sales endpoint such as:

```text
GET /api/intelligent-sales/screen-pop/matches?phone=<caller-id>
```

The endpoint must:

1. normalize the caller ID with the existing `phoneDigits()` behavior;
2. require a complete number (at least ten normalized digits for the current North American data);
3. match exact normalized values against both `phone` and `phone_alt` using the existing indexed
   path;
4. apply the same tenant, role, ownership, assignment, and `records.view_all` visibility rules used
   by the CRM boards and record card;
5. load only the open roles and opportunities needed to select a destination; and
6. return a bounded DTO, never raw database rows.

Example response:

```json
{
  "normalizedPhone": "5552001000",
  "matches": [
    {
      "bpId": "00000000-0000-0000-0000-000000000000",
      "label": "Example Carrier LLC",
      "preferredView": "opps",
      "preferredOpportunityId": "00000000-0000-0000-0000-000000000001",
      "stageLabel": "Qualified",
      "reason": "Active opportunity"
    }
  ]
}
```

### Destination selection

For each visible matched business partner, choose the suggested destination deterministically:

1. **Opportunity** when the partner has an active, non-terminal opportunity. If several exist,
   prefer one owned by/assigned to the current rep, then the most recently updated.
2. **Account** when the partner has an active account/customer role and no active opportunity.
3. **Lead** when the partner has an active lead role and neither condition above applies.
4. **Partner record** when the phone matches a visible partner but none of those roles is active.

The permanent `bp_id` remains the record identity. `preferredView` and
`preferredOpportunityId` choose the part of the record to focus; they must not create duplicate
business partners.

### Prompt behavior

- One confident match: show caller/record summary and **Open** / **Dismiss** actions.
- Several matches: show a chooser; never auto-open the first record.
- No match: show **Unknown caller** with **Search CRM** and, if the user has permission,
  **Create lead**. Do not create anything automatically.
- Withheld, anonymous, malformed, or short caller ID: show **Caller ID unavailable** and perform no
  CRM lookup.
- A prompt is non-modal and must not prevent the user from operating the CRM or RingCentral client.
- Clicking a match switches/focuses the appropriate Account, Opportunity, or Lead context and opens
  the existing record card. The user remains in control of navigation.
- Dismissal applies to the current `telephonySessionId`; subsequent snapshots of the same call do
  not reopen it.

## Security and privacy requirements

- RingCentral credentials are entered only on RingCentral-hosted pages. OSHAL never handles a
  RingCentral password or MFA secret.
- OAuth uses Authorization Code with PKCE, signed short-lived state, exact redirect matching, and a
  one-time callback attempt.
- Tokens remain encrypted and owner-scoped in the core connector store. They never enter a prompt,
  model environment, generic bot payload, package source, browser storage, or log.
- RingCentral events are routed by the authenticated OSHAL `user_sub`, not by a browser-supplied
  extension id, email, or phone number.
- SSE requires the normal OSHAL session and must fail closed when caller identity is absent.
- CRM matching applies tenant and record-visibility predicates before returning labels or ids.
- Logs must not contain raw access/refresh/WebSocket tokens. Operational logs should avoid full
  caller numbers; use a one-way correlation hash or last four digits only when necessary.
- Caller data is transient. v1 does not persist a call-event history merely to support a screen-pop.
- The integration is read-only from RingCentral's perspective and cannot answer or manipulate a
  call.

## Failure handling and observability

Emit structured metrics without token or full phone-number values:

- OAuth start, success, denial, state failure, and token-exchange failure counts.
- Active RingCentral listeners and active CRM SSE clients.
- WebSocket connect, recover, resubscribe, close reason, and retry counts.
- Ringing events received, deduplicated, delivered, unmatched, and suppressed by visibility.
- Time from RingCentral event receipt to CRM prompt delivery.
- Refresh success/failure and connections requiring reauthentication.

User-facing errors must distinguish:

- operator configuration missing;
- user not connected;
- popup blocked;
- user denied consent;
- required RingCentral scope/permission missing;
- RingCentral authorization expired/revoked;
- temporary listener outage; and
- CRM match unavailable.

The UI may retry temporary listener failures, but must never claim **listening** until the
RingCentral subscription is acknowledged.

## Cost and entitlement

RingCentral states that production API access is included with existing RingEX plans. This
screen-pop adds no calls, messages, or call-control operations and does not intentionally incur a
per-event API charge. A separate watermarked developer sandbox is optional; RingCentral currently
lists it at $10/month when billed annually or $12 month-to-month for two included extensions.
Plan entitlements and prices must be rechecked before purchase or rollout.

OSHAL infrastructure impact is one outbound RingCentral WebSocket per active connected CRM user,
plus one shared listener for that user's browser tabs. No public RingCentral webhook endpoint or
polling service is required for v1.

## Implementation work

### Core connector/runtime

1. Register `ringcentral` in the connector OAuth provider registry.
2. Add credential resolution for `RINGCENTRAL_CLIENT_ID` and
   `RINGCENTRAL_CLIENT_SECRET`.
3. Enable PKCE S256 and the RingCentral-specific token-exchange/refresh adapter.
4. Add the RingCentral extension account lookup and persist `owner_id`/extension identity.
5. Pass RingCentral environment variables through local/production deployment manifests.
6. Add popup completion and safe return-to-CRM handling to the generic OAuth ceremony.
7. Add an owner-scoped listener manager, RingCentral WebSocket adapter, event normalization,
   dedupe, recovery, and SSE route.
8. Add disconnect/revoke and listener cleanup.

### Intelligent Sales package

1. Declare the `ringcentral` connector dependency.
2. Add connection/listener status and **Connect RingCentral** UI.
3. Add the visibility-safe phone match/ranking endpoint.
4. Add SSE lifecycle handling and the non-blocking screen-pop/chooser.
5. Open the existing record card focused on the selected role/opportunity.
6. Add unknown-caller, reconnect, popup-blocked, and permission-denied states.

### Tests

- Provider registry: correct production endpoints, two scopes, PKCE, refresh tokens, and exact
  redirect override.
- OAuth: forged/expired/replayed state rejected; wrong user rejected; missing verifier rejected;
  tokens encrypted; popup response contains no secret.
- Token refresh: per-connection serialization and atomic refresh-token rotation.
- Listener: one WebSocket per active user, multiple tabs share it, last-tab close releases it.
- Event parser: only inbound `Ringing` entries emitted; queue calls supported; malformed/anonymous
  caller IDs handled; duplicate snapshots produce one prompt.
- Isolation: one user's RingCentral event cannot reach another user's SSE client or CRM match.
- CRM lookup: normalized exact match on both phone columns; visibility rules enforced; destination
  priority Opportunity -> Account -> Lead -> Partner.
- Browser: popup success, popup denial, popup-blocked redirect fallback, prompt chooser, dismiss, and
  record open.
- Live acceptance: two real RingCentral users connect independently; a known inbound call prompts
  only the ringing rep; an unknown caller shows no record; disconnect stops delivery.

## Acceptance criteria

The feature is complete when all of the following are true:

1. A normal CRM user can connect RingCentral from Intelligent Sales without Developer Console
   access, a pasted JWT, or sharing a password.
2. The production authorization request and token exchange both use exactly
   `https://gsquared.oshal.ai/api/connect/ringcentral/callback`.
3. Only `ReadPresence` and `WebSocketsSubscription` are required for the v1 screen-pop.
4. Opening the CRM activates one user-scoped listener; closing the last CRM tab releases it.
5. A real inbound ringing call produces one prompt for the correct rep under normal network
   conditions, with no polling.
6. Known numbers return only records that rep is authorized to view and offer the deterministic
   Account/Opportunity/Lead destination.
7. The user must click before navigation; no call-control API is invoked.
8. Refresh rotation, reconnect, dedupe, cross-user isolation, disconnect, and failure states pass
   automated tests.
9. No RingCentral secret or token is exposed to the browser, package, logs, model, or workspace.
