# Security Posture (current state, honest)

This is a point-in-time, no-spin posture map for the OSHAL / Open Swarm harness.
Status values:

- CLOSED: a control is in force today, on by default.
- PARTIAL: a control exists but has a known gap, or is only opt-in.
- OPEN: the control is not in force today; a path to harden may exist but is not engaged.

The hardening modules referenced below live in
`src/features/security/hardening/` and are all OFF by default. Turning any of
them on requires an operator to set an env flag and (for most) wire one line into
`src/app/server.ts`. Nothing here changes runtime behavior until a flag is set.

| Area | Status | What is true today | Flag / how to harden | Residual risk |
|---|---|---|---|---|
| Envelope crypto (per-user DEK) | PARTIAL | Built but OFF by default. With the flag unset, connector tokens are encrypted at rest with one shared key (`SHA256(SESSION_SECRET)`) — strong against one user reaching another's row, but not a per-user vault. The per-user DEK envelope (`src/app/routes/connector-token-crypto.ts`) is implemented and tested but only active when the flag is set; on the DEK path it falls back to the legacy key on error (fail-soft, not fail-loud). | Set `OSHAL_ENVELOPE_CRYPTO=true` (default off). `decryptToken` is format-aware so the flag flips without stranding legacy tokens; new writes upgrade to `v2:` per-user DEK blobs on next connect/refresh. | Until enabled, a leak of both DB access and `SESSION_SECRET` decrypts every user's tokens. With it on, one user's DEK compromise exposes only that user. Behavior proven in `tests/connector-token-crypto.spec.ts`. |
| MOCK_OIDC dev bypass | CLOSED | Off by default. The auth bypass only activates when explicitly set for local dev. | Keep `MOCK_OIDC` unset in any shared/hosted environment. | If an operator sets it in a non-dev environment, auth is fully bypassed. Treat as a deploy-config invariant. |
| shell:false RCE guard | CLOSED | Test-asserted: the fast-intake spawn must not use `shell: true` (regression test in `tests/security-review-fixes.spec.ts`). | N/A (enforced by test). | Other spawn sites are not all covered by the same assertion; new spawns should be reviewed for `shell: true`. |
| Tool-exec fail-closed | PARTIAL | In force by default: cli executor command templates are rejected at registration if their static segments contain shell metacharacters (`; \| & > < $( \` ${` newline) or unsupported `{tokens}` (`cli-command-validator.ts`, throws on the write path, skip-and-warn on restore); and unregistered exec/code-eval tools (`execute_command`, `run_command`, `shell`, `bash`, `sh`, `exec`, `eval`, `spawn`) always fail closed (`tool-auth-interceptor.ts`). Proven in `tests/unit/tool-exec-failclosed.spec.ts` (17 cases). | Set `OSHAL_TOOL_AUTH_STRICT=true` (default off) to deny ANY unregistered tool, not just the exec set. | By default, non-exec tools missing from the auth registry still fall through (graceful-allow) — strict mode closes that. Template validation blocks injection-through-template but NOT a manifest that names a destructive binary directly; per-execution sandboxing (planned) is the containment for that. |
| Secret-scan publish gate | CLOSED | `scripts/build-public-baseline.sh` refuses to produce a public baseline commit if a secret-looking value survives the sanitize pass. | N/A (gate runs in the publish SOP). | The gate covers the curated snapshot only; it does not scrub the PRIVATE repo's existing history. Rotation + history scrub remain operator tasks. |
| Content-Security-Policy (CSP) | OPEN | Disabled today (`helmet({ contentSecurityPolicy: false })`) because the cockpit UI uses inline scripts/styles. | Opt-in strict module now available: `cspFromEnv()` in `strict-csp.ts`. Set `OSHAL_STRICT_CSP=on`; use `OSHAL_CSP_REPORT_ONLY=on` first to migrate inline scripts (nonce support included). | Until enabled, there is no CSP, so an injected inline script is not blocked by CSP. The module is opt-in; merging it does not turn CSP on. |
| Rate limiting | PARTIAL | Global limiter (1000/min) is in force, but it SKIPS requests with no `X-Forwarded-For`, so the internal mesh / direct-to-origin path is unlimited. | New presets in `rate-limit-presets.ts`: `internalMeshLimiter` (covers the no-XFF gap, `OSHAL_RATE_LIMIT_INTERNAL`) and `expensiveOpLimiter` (tight per-IP cap for LLM/intake, `OSHAL_RATE_LIMIT_EXPENSIVE`). All default disabled. | The no-XFF gap remains open until `OSHAL_RATE_LIMIT_INTERNAL` is enabled. Anything reaching the origin without going through cloudflared is currently unthrottled. |
| Webhook HMAC | PARTIAL | The Alertmanager webhook is token-gated with a shared bearer secret but has NO HMAC, so body integrity is not proven. | New helper `webhook-hmac.ts`: `hmacWebhookGuard({ secretEnv, header, prefix })` fail-closes when its secret env is set, no-op when unset (opt-in per webhook). Supports GitHub `sha256=` and Slack `v0=` schemes. | Until a secret env is set per webhook, body integrity is unverified. A leaked bearer token still authenticates a request whose body could be altered in transit. |
| DB-enforced RLS | CLOSED (live on oshal-local 2026-06-27) | RLS is enforced platform-wide on 84 tables across 3 tiers (user-private, tenant-shared, backend) per **ADR-076** / migration `060-platform-rls-tenancy.sql` — not just the original tickets/workspaces/access-audit/chat-tasks four. The runtime connects as the non-superuser, non-`BYPASSRLS` role `oshal_app`, which OWNS the tables (so startup/migration DDL still runs) while `FORCE ROW LEVEL SECURITY` scopes even the owner; the `SECURITY DEFINER` tenant helper stays owned by the superuser to avoid policy recursion. The GUC wrapper is on by default. Live verification on oshal-local: a normal user sees only their own rows (0 cross-user reads), strangers see 0, the system/operator context sees all, and tenant sharing works. | A fresh deploy must run `docs/governance/app-role-provisioning.sql` (create `oshal_app`, reassign table/sequence/view ownership) and point the runtime `DATABASE_URL` at it; see **ADR-076** and `docs/governance/RLS-RUNBOOK.md`. Break-glass rollback: repoint `DATABASE_URL` at the superuser role or set `OSHAL_DB_GUC=off`. | Residual risk is now limited to deferred tables that lack an owner column and remain app-layer-scoped only: `personal_graph_nodes/edges`, `chat_messages`, `agent_memories`, `knowledge_memory_documents`, and the `lm_*` student tables. The TimescaleDB store (`oshal_ts`) is a separate DB, not yet covered. |
| RBAC roles | OPEN | Not in force today. Authorization is largely a single authenticated tier plus a separate platform-admin plane. | Role scaffolding added separately (out of this module set). | No fine-grained role separation among tenant users yet; least-privilege is coarse. |
| Audit export | OPEN | Not in force today as a first-class export endpoint. Audit/dispatch trails exist internally (Security Center audit scanner) but there is no operator-facing signed export. | Export endpoint added separately (out of this module set). | No tamper-evident, exportable audit record for external review yet. |
| CLI-token (PAT) bootstrap mint | CLOSED (merged 2026-07-31, deployed + re-verified 2026-08-01, PR #83) | The session-less bootstrap mint (`POST /api/cli-tokens` with the service secret + `x-oshal-user-sub` header — i.e. `swarm-cli login --secret`) is operator-only via `isOperatorIdentity` (fail-closed on an empty allowlist) and time-boxed by `OSHAL_CLI_TOKEN_BOOTSTRAP_TTL_DAYS` (default 30 days, reusing the `expires_at` column). Session (cockpit) mints are unchanged and still non-expiring. Closes the pre-fix cross-user takeover where a prompt-injected bot holding `SWARM_SERVICE_SECRET` could mint a permanent PAT for an arbitrary victim sub — confirmed live pre-fix, and the same exploit now returns `403 operator_required`. Guard: `tests/unit/cli-token-auth.spec.ts`. | Configure `OSHAL_OPERATOR_EMAILS` / `OSHAL_OPERATOR_SUBS` so an operator identity exists; tune `OSHAL_CLI_TOKEN_BOOTSTRAP_TTL_DAYS`. | Operator-minted bootstrap PATs expire in ~30 days, so a `swarm-cli login --secret` flow must re-login every 30 days. Session-minted tokens remain non-expiring — revoke on compromise. |
| Controller-to-bot execution delegation | PARTIAL | Ed25519 delegation is implemented and fail-closed whenever key material is configured: the controller alone signs; bots verify only with a public rotation ring; every token is bound to issuer, principal namespace, subject, local agent, task, the complete canonical request-body SHA-256, exact `swarm:execute` scope, and time; Redis atomically enforces single use. Signed mode also prohibits unsigned mesh, batch, legacy-runtime, and localhost fallback execution. | Generate and role-separate `OSHAL_DELEGATION_SIGNING_KID` / `OSHAL_DELEGATION_SIGNING_PRIVATE_KEY` on the controller and `OSHAL_DELEGATION_PUBLIC_KEYS` on every bot. Follow [http-delegation.md](./http-delegation.md). | Opt-in for rollout compatibility: with no keys, absent tokens are still accepted and the disabled posture logs a warning. A half rollout intentionally stops execution. Legacy background jobs that retained only `sub`, not its verified issuer, stop until provenance is persisted. `X-Service-Secret` remains an independent fleet-wide credential and the read-side confused deputy below remains open. |
| Bot safety / prompt injection | PARTIAL | The unattended tool-approval gate is pinned fail-closed: bots on the swarm-dispatch path do NOT auto-approve `execute_command` / file-write / MCP tools. The decision plus its accidental key-name-mismatch history live in `any-bot/server/controllers/tool-approval-policy.js`, guarded by `tests/unit/tool-approval-policy.spec.ts`. Unregistered exec/code-eval tools also fail closed (see the Tool-exec fail-closed row). Worker bots connect as the non-superuser `oshal_bot` role, so a fooled bot cannot bypass RLS. | Set `OSHAL_TOOL_AUTH_STRICT=true` to deny unregistered non-exec tools; wire `ToolAuthInterceptor` on every executor path (today it is wired only when `switchFrameworkService` is supplied). | STILL OPEN: no fencing of untrusted content on the ticket-dispatch path — `assemblePromptForAnyBot` joins persona, org memory, handovers and the raw ticket body at one trust level, and `SwarmMemoryService` re-injects prior agent output as authoritative (wormable). Also open: a **read-side confused deputy** — because every bot holds the fleet `SWARM_SERVICE_SECRET`, an injected bot can assert an arbitrary victim sub and read that user's data on trusted-service read routes (confirmed live on `/api/graph` and `/api/jarvis` `/history` `/tasks` `/overview`; `/api/messages` returns 401). Read-only, no credential minting. Durable mitigation: per-bot service secrets + tighter caller-scoping. No adversarial-prompt regression tests exist. See SECURITY-HARDENING.md §4.8 and ADR-122. |
| Route auth (default-deny by convention) | CLOSED | OIDC is `authRequired:false`, so every route must opt into `requiresAuth`; a live unauthenticated sweep of the sensitive-route set returned 401, with only `/health` and `/api/readiness` public by design. Enforced by the route-auth inventory in `tests/unit/server-route-auth-inventory.spec.ts` (the by-design-public allowlist lives in `tests/helpers/unguarded-route-allowlist.ts`). | Add new sensitive routes behind `requiresAuth`; the inventory test fails if one is missed. | A newly-added route that forgets `requiresAuth` is anonymous-callable until the inventory catches it. **Note:** `requiresAuth` is an authentication wall, not caller-scoping — routes mounted `serviceSecretOr(requiresAuth)` additionally trust a fleet-secret `x-oshal-user-sub` assertion; see the Bot safety row for the read-side confused-deputy that follows. |

## Notes on honesty

- Every "available" hardening control in this set is OPT-IN and defaults OFF.
  Listing a control here does not mean it is enforced; read the Status column.
- CSP, the internal-mesh rate gap, and webhook HMAC are the three items this
  module set most directly addresses, and all three remain OPEN/PARTIAL until an
  operator sets the relevant flag and wires the one-line activation.
- Credential rotation and git-history scrubbing are operator-run prerequisites
  for any public release and are NOT performed by these modules. See
  `docs/release/public-release-checklist.md`.
