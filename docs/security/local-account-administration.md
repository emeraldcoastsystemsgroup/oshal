# Existing accounts and local account administration

The Users page lists existing local accounts and verified external identities without replacing either. Invitations, re-invitations and enable/disable actions use the existing local account APIs. A newly created invitation link is displayed once to the administrator for delivery; existing passwords and second-factor secrets are never listed. External account sign-in and suspension remain controlled by the identity provider. Application permissions are managed in Access Administration.

First-install setup is closed when the deployment already contains any local account, a `swarm_roles` row, a verified principal record, or a completed installer ceremony. This includes disabled accounts and historical provider records. The public setup state reports only whether setup is required. The proof-bound installer transaction checks the same established identity stores before creating an account and root. Existing operator recovery remains available; an empty role table alone never authorizes a public root claim.

Local account suspension and administrator-driven credential recovery lock the local account and role tables in a single database transaction. Disabling the current root is refused until root is explicitly transferred. A different administrator or a service credential cannot issue a new root invitation/password-reset link, clear root second-factor enrollment, or relax its second-factor requirement. Root may manage its own credentials only through its authenticated local issuer and exact current subject. These controls do not change the existing mailbox-based self-service password reset or local installer proof/recovery mechanisms.

The transaction reads the current role after concurrent role writes complete; it never trusts the browser's role display. Existing account status operations still invalidate local sessions through their token version. Provider history does not create local accounts or merge users by email.

Regression coverage: `tests/unit/local-account-administration.spec.ts` runs the real APIs and root transfer races against disposable PostgreSQL; `tests/unit/users-administration-browser.spec.ts` drives the actual Users page in Chromium. Existing login and installer proof suites remain required. Fixtures create only temporary databases and use no deployed account or provider credentials.
