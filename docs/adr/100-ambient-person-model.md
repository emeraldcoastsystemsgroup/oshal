# ADR-100 — Ambient Person Model: transcript-canon person profiles, recall with receipts, and the audio-clip rejection

- **Status:** Accepted — Phase 1 shipped as Ambient Recall extension app; Phase 2+ remain future work
- **Date:** 2026-07-17
- **Author:** maintainer@emeraldcoastsystemsgroup.com
- **Related:** [ADR-036](036-bot-owned-application-architecture.md) (bot-owned domain), [ADR-045](045-two-tier-graph-database-and-connector.md) (graph tier + adoption rule), [ADR-050](050-unified-assistant-route-orchestrator.md) (Jarvis), [ADR-066](066-personal-knowledge-graph.md) (the *other* personal graph — deliberately not used), [ADR-076](076-tenant-aware-rls-and-least-privilege-db-role.md) (RLS scope), [ADR-083](083-knowledge-owner-call-out-routing.md) (call-out routing), [ADR-087](087-access-roles-jarvis-visibility-scoping.md) (accessRoles), [ADR-091](091-pgvector-rag-engine.md) (pgvector engine), [ADR-097](097-app-suites-primary-categorization.md)

## Context

Opt-in ambient listening already ships: speaker-attributed transcript segments in the main Postgres (`ambient_transcript_segments`, migration 068), voiceprint profiles for every distinct voice heard including non-users (`ambient_speaker_profiles` / `ambient_speaker_assignments` / ordinal counters, migration 069), all owner-RLS'd via `buildOwnerRlsPolicyStatements` and covered by data-lifecycle export/delete through structural discovery of `user_sub`/`owner_sub` columns. The operator wants to grow this into a **Person Model**: per-heard-person profiles that accrete over time (topics, asks, commitments, presence), tone/intent inference per utterance, natural-language recall with receipts ("Jarvis, how many times has Ella mentioned volleyball today? Play it back."), trend and relationship questions, and — optionally — audio-clip retention with playback-on-demand.

The data is multi-modal on paper (relational identity, vector semantics, dated-edge graph, time series), and all four candidate engines already run in compose (main Postgres with pgvector 0.8.5 and `RAG_ENGINE=pgvector` active, `oshal-tsdb` TimescaleDB, ChromaDB, ArangoDB per-person DBs behind the ADR-045 connector). The design question is which engines *personal* data may honestly touch, given repo law: Postgres is the system of record with rebuild-from-canon required for any derived index; RLS on all new personal tables; ADR-036 puts all reasoning on an accountable bot; ADR-045 says don't force graph where relational fits.

Two legal/trust facts frame everything. First, the promise **"Raw audio is never stored"** is published on more surfaces than one: the consent panel (`src/api/jarvis-ambient.js:270`), `README.md:190` and `:217`, `site/oswarm.ai/index.html:1372`, `docs/architecture/jarvis-architecture-and-flow.md:404`, and the panel copy is pinned verbatim by `tests/unit/jarvis-ambient-client.spec.ts:77` — any wording change must land on all six or the pinning test silently freezes stale copy. Second, Fla. Stat. §934.03 (all-party consent) governs interception of **oral communications regardless of storage format** — the *existing transcript pipeline* is already inside its scope, so the legal posture must cover transcription and inference, not only the audio-clip question. To be plain about today's state: heard non-users are transcribed and voiceprinted with no consent artifact at all; this ADR makes per-person *modeling* opt-in and gives heard people a purging opt-out, but it does not and cannot retrofit consent onto capture itself — that rests on an owner household-notice obligation made explicit in §5.

Three competing designs were evaluated (single-engine consolidator; four-engine temporal-KG maximalist; consent-first). This ADR records the consolidator posture with the consent machinery and idempotent-projection mechanics grafted from the other two.

## Decision

### 1. Engine posture: one engine — the main Postgres

Every Person Model store lands in the **main Postgres** (relational canon + generated-tsvector FTS + pgvector via the existing `rag_chunks` table). Rationale, recorded so successors inherit it:

- **TimescaleDB is disqualified for personal data.** ADR-076 explicitly scopes `oshal-tsdb` out of RLS/least-privilege; it is reached as superuser `oshal`, has no `oshal_app` role, no migration mechanism, and no `user_sub` column anywhere. Ambient trend volume (hundreds of rows/owner/day) is ~4 orders of magnitude below `world_metrics`; a rollup table with a composite index is the honest tool.
- **ArangoDB is deferred, not adopted.** The ADR-045 adapter keys edges on `(from,type,to)` and *overwrites* props on re-upsert — structurally wrong for multi-occurrence dated edges — and `arangodb_person_graph` sits in `KNOWN_EXPORT_GAPS` with no exporter/deleter. Every stated relationship story is ≤2 hops, which ADR-045's own adoption rule says belongs in SQL. **Escalation trigger** (both required): a needed query exceeds 2 hops or requires recursive traversal SQL can't express cleanly, AND an Arango person-graph exporter/deleter has closed the export gap first. If the trigger ever fires, the sanctioned projection shape is: reified `utt:<segment_id>` nodes carrying `{at, tone, intent, enrichment_version}` props plus props-summarized dated `MENTIONS`/`ASKED` edges (`{first_at, last_at, count, days[]}`), swept by `rawQuery` REMOVE on stale `enrichment_version`; access only via `/api/graph` (`getPersonGraph(sub)`), with the bot authoring AQL as reason-output and the **controller** executing it through the connector (a Form B concierge cannot shell out), degrading to the relational co-occurrence query with a one-time note on `503 graph_engine_unavailable`.
- **ChromaDB is redundant.** `RAG_ENGINE=pgvector` is the active engine; a second vector store for the same 384-dim MiniLM embeddings is pure drift surface.
- **The ADR-066 `personal-graph` slice is not used** — no ownership column (a declared export gap), off by default, and deliberately named apart from the ADR-045 graph.

Drift surface: the only derived index (embeddings) lives in the **same database** as canon, with a drift ledger (§2). Honesty note: `rag_chunks` row-level security is currently **inert** for engine-written rows — `PgvectorRagEngine.addChunks` never populates the dedicated `owner_sub`/`tenant_id` columns (owner rides only in metadata JSONB) and the engine's own pool bypasses the GUC wrapper — so isolation there is today the app-level permission filter, the same posture Haven ships. §2's Phase-3 **entry gate** makes column-level ownership real *before* the first ambient chunk exists; until then §1 claims only same-database co-location, not database-level RLS.

### 2. Storage — migration `scripts/migrations/088-person-model.sql` (NEW; 088 is the next free number)

Canon is the existing ambient/speaker tables. All NEW tables carry `user_sub`/`owner_sub`, get `buildOwnerRlsPolicyStatements`, and are picked up automatically by data-lifecycle export/delete via `discovered-exporters.ts` (with the one deliberate retention carve-out noted below):

| Table (NEW) | Shape | Role |
|---|---|---|
| `ambient_utterance_enrichment` | PK `(segment_id, taxonomy_version)`; segment_id FK→`ambient_transcript_segments` ON DELETE CASCADE; user_sub; topics JSONB; tone; intent; ask_text; commitment_text; confidence; model; taxonomy_version; enrichment_version; is_inference BOOL DEFAULT TRUE; enriched_at. GIN on topics; index (user_sub, enriched_at). | Versioned inference layer beside canon — taxonomy revisions create a new generation, never silently overwrite; stale generations are sweepable on rebuild. |
| `ambient_person_asks` | ask_id UUID PK; owner_sub; profile_id FK→`ambient_speaker_profiles` CASCADE; segment_id FK CASCADE; kind CHECK ('ask','commitment'); text; **source_quote TEXT (verbatim transcript line); model; confidence; is_inference BOOL DEFAULT TRUE**; dedupe_key (sha of segment_id+kind), UNIQUE(owner_sub, dedupe_key); status CHECK ('open','done','dismissed') DEFAULT 'open'; created_at; resolved_at. | Follow-up ledger with provenance. Extraction is derived; **status is canonical user state** — rebuild upserts on dedupe_key and never touches status. |
| `ambient_person_topic_daily` | PK (owner_sub, profile_id, local_date, topic); mention_count; **profile_id FK→`ambient_speaker_profiles`(profile_id) ON DELETE CASCADE**. | Pure-SQL trend rollup; local_date from `ambient_user_settings.time_zone`. **Retention-bounded**: the nightly sweep purges rows older than the owner's `transcript_retention_days` — a recall aid, never a permanent dossier. |

| `ambient_speaker_consents` | consent_id UUID PK; owner_sub; profile_id FK→profiles ON DELETE CASCADE; scope CHECK ('transcript','voiceprint'); status CHECK ('granted','declined','revoked'); is_minor BOOL; method CHECK ('in_app','owner_attested','written'); evidence_segment_id FK→segments **ON DELETE SET NULL**; recorded_at. **Append-only enforced by a BEFORE UPDATE/DELETE trigger (the migration-061/083 pattern), shipped in 088.** Latest row per (profile, scope) is current. | Per-heard-person notice/consent ledger (Phase 2), gating semantics in §3/§5. **Deliberately NOT `audio_clip`/`guardian_granted`** — those enum values exist only to serve the rejected clip mode and are added only by a successor migration if the §5 gate ever fires. Phase 2 also adds `ambient_speaker_consents` to `RETAINED_DISCOVERED_TABLES` in `discovered-exporters.ts` (export-only; retention reason: honoring a decline requires keeping the decline). |

| FTS on canon | `ALTER TABLE ambient_transcript_segments ADD COLUMN fts tsvector GENERATED ALWAYS AS (to_tsvector('english', transcript_text)) STORED` + GIN (the `rag_chunks` 070 pattern). | Phase-1 exact-recall leg via `websearch_to_tsquery`; remains the permanent exact leg after semantic search lands. |
| Semantic index (Phase 3) | Rows in existing `rag_chunks`, collection `ambient-recall`, **deterministic chunk ids `pm:<segment_id>`** written through `PgvectorRagEngine.addChunks` (exported via the `@/features/rag` barrel — NEW export; no deep imports). Metadata `{profile_id, segment_id, captured_at}` **plus the dedicated `owner_sub` COLUMN populated (Phase-3 entry gate)**; retrieval always passes `{userSub, allowPublic:false}` (the Haven `'user-model'` precedent) so `searchAllCollections` cannot leak it. | Paraphrase recall. `ON CONFLICT (chunk_id) DO NOTHING` makes incremental ingest and full rebuild idempotent — no delete-then-reingest ordering dependency. |

**Drift and deletion control.**
(a) *Segment deletes:* FK CASCADE from `ambient_transcript_segments` shreds `ambient_utterance_enrichment`, `ambient_person_asks`, and `ambient_person_relations` rows automatically on `DELETE /days/:date`, `DELETE /data`, the retention sweep, and data-lifecycle delete; `evidence_segment_id` goes SET NULL. `ambient_person_topic_daily` is an aggregate with no segment FK **by design** — it converges only via the rollup rebuild (a distinct acceptance criterion, not a cascade claim).
(b) *Vector chunks have no FK and get explicit parity:* every segment-deleting path above (plus the §5 decline purge) calls a person-model **chunk purge** keyed by `pm:<segment_id>`; the nightly job runs an anti-join backstop (`rag_chunks` `collection='ambient-recall'` vs surviving segments) that deletes orphans. No transcript text may outlive its segment in any store.
(c) *Profile deletes:* the FK columns on topic_daily and relations CASCADE on `DELETE /speakers/:profileId`; the endpoint additionally hooks the same no-LLM refresh used for merge/assignment, which also purges any legacy `person:<profile_id>` ref rows lacking the FK column. Renames and merges converge same-day via that hook.
(d) *Retention:* the nightly sweep bounds topic_daily and relations to `transcript_retention_days`, matching the expectation the settings UI creates.
(e) *Rebuild:* `scripts/person-model-rebuild.ts` (NEW) is **pure SQL/IO** — it re-projects rollups, relations, and vector chunks from **stored** `ambient_utterance_enrichment` rows and never runs an LLM. Re-enrichment for a new `taxonomy_version` is performed only by the accountable bot through the §3 pipeline. Ask statuses provably survive rebuild via dedupe_key upsert.
(f) The nightly job reconciles counts and advances watermarks in `person_model_projections`.

### 3. Enrichment pipeline (ADR-036: the bot reasons, the controller pre-fetches)

- **Accountable bot:** `ambient-analyst` (NEW) — a **Form B concierge node** per `docs/building-a-bot.md` (reason-only, no shell-out): registry entries in **both** `swarm-bot-registry.ts` and `swarm-bot-registry-local.ts` with `container: 'oshal-api'`, NEW persona `ai-lab/bot-personas/ambient-analyst.yaml` with a pinned JSON output contract, unique v4 agentId matching the persona, `accessRoles: ['operator','swarm','jarvis']` (ADR-087), **plus a crisp `selector_descriptor` and `routing_keywords` so ADR-083 call-out routing can select it for any ticketed work**. All inference goes through `executeBotOrInline(…, {userSub, agenticMode: true, direct: true})` so cost lands in `chat_tasks` under its agentId. The controller never calls an LLM. Introduced in **Phase 2** — Phase 1 needs no new bot.
- **Per-person opt-in gate:** enrichment, ask extraction, rollups, relations, and vector ingest run for a profile **only when its latest transcript-scope consent row is `granted`** (the owner's in-app affirmation that the person has been informed — §5). The owner's own `self` profile is granted implicitly by enabling ambient. A profile whose latest ledger row carries `is_minor=TRUE` is treated as **declined for the entire inference layer** regardless of granted status (children cannot consent — the §5.2 argument applies to profiling, not just clips); transcript attribution, an existing shipped feature, is unchanged.
- **Micro-batch trigger:** `src/app/ambient-enrichment-runtime.ts` (NEW), cloned from the `startAmbientReviewRuntime` shape (unref'd interval, env-clamped, default 5 min): each sweep selects up to ~50 unenriched, gate-passing attributed segments per owner and issues **one** structured-JSON call per owner-batch. Kill switch env `OSHAL_AMBIENT_ENRICH=0` (NEW); Haven-style throttle. **This is a recorded, accepted deviation from ADR-036's transport rule** (scheduled LLM work should ride a dedicated ticketType + workflow): ticket types can only be registered via the built-in `WORKFLOW_PIPELINES` table or a swarm-app manifest, and this design deliberately adds neither (§6) — editing core `WORKFLOW_PIPELINES` for a 5-minute sweep is framework creep, and an ambient manifest fails the ADR-097 who-is-it-for test today. Compensating controls: cost capture in `chat_tasks` under ambient-analyst is intact, batches are small and bounded, the kill switch is one env var, and a failed sweep simply retries next interval (segments stay unenriched, nothing is lost). A `person-model-enrich` ticketType is **reserved** for if/when an ambient manifest ever ships, at which point micro-batches move onto it.
- **Nightly pass is not a ticket either:** the rollup re-aggregation, retention purge, chunk anti-join, projection reconciliation, and stale-ask sweep are **pure SQL — zero LLM — and therefore controller-permitted** under ADR-036's own distinction; they run from the same interval runtime on a nightly schedule.
- **Taxonomy v1 (text-level, CHECK-constrained):** tone `neutral|warm|excited|frustrated|upset|urgent|humorous|tired`; intent `inform|question|ask_request|commit|plan|recall|vent|banter`. `ask_request` → asks row (kind `ask`); first-person `commit` → kind `commitment`; 1–3 lowercase topic slugs per utterance. Everything stored with model + confidence + `is_inference=TRUE`. **Rendering rule (applies to enrichment, asks/commitments, and relation-derived answers alike):** every surface presents these as "OSHAL's read," never transcript fact — an extracted ask is always shown beside its verbatim `source_quote` so the user can judge the extraction. **Acoustic prosody is deferred** — a later sidecar-model phase writes the same tone column with a different `model` string; no schema change.

### 4. Query federation — the Ella query is the canonical Phase-1 acceptance scenario

"Jarvis, how many times has Ella mentioned volleyball today? Play it back."

1. **Capture (unchanged rails):** `jarvis-ambient.js parseWakeCommand` → `onWakeCommand` → `handleInput` → `POST /api/jarvis/ask` (jobId + `GET /ask/result` polling).
2. **Deterministic recall guard (NEW)** beside `detectProviderBoundHandoff`: recall shapes ("how many times has X mentioned Y…", "what did X say about…", "play it back") match **before any model turn** — counts are never answered from model memory. **File-cap discipline:** the matcher and receipts assembly live in the `src/features/person-model/` slice (exported via its barrel); `jarvis-routes.ts` — already past the 800-code-line decomposition threshold — gains only a one-line hook call.
3. **Controller pre-fetch (cheap I/O, no LLM):** NEW FSD slice `src/features/person-model/` exposes `recallQuery(pool, sub, {personName, terms, range})` — resolve "Ella" via `ambient_speaker_assignments.custom_name` → membership `display_name` → "Unidentified Person N" (the `profileLabel` order); owner-local "today" from `ambient_user_settings.time_zone`; one SQL over segments using the FTS column (`fts @@ websearch_to_tsquery`) OR an enrichment-topic match, RLS backstopping the explicit `user_sub` WHERE.
4. **Phrasing:** Phase 1 prepends the receipts block to the message (the `buildToolsBlock` prepend precedent) and the **existing Jarvis bot** phrases it via `runJarvisBot` (cost under `a0000000-0000-0000-0000-000000000050`) — zero new registry entries in Phase 1. **Phase 2 routing rides live code paths only:** the recall guard extends to dispatch person-model intents (profile questions, ask lookups, trends) to `ambient-analyst` via `executeBotOrInline` directly — the same pre-model dispatch pattern `providerBoundIntent` uses today — and ticketed/background asks reach it via ADR-083 call-out (the registry `selector_descriptor`/`routing_keywords` from §3). The `AppRoute` delegate table is **not** used: it lives only inside `orchestrate()`, which has zero call sites; reviving that path is explicitly out of scope.
5. **Playback:** the response carries `receipts[]` (count, quoted lines, timestamps, segment_ids); the Jarvis surface re-speaks quoted lines via the **`voice` kernel skill** — always in the assistant's voice. **Voice-cloning a heard person is rejected outright** (§5). No raw audio exists to play.
6. **Routes (NEW):** `createPersonModelRoutes()` mounted `app.use('/api/jarvis/ambient/person', serviceSecretOr(requiresAuth), …)` — the established trusted-service mount shape, after the guest gate, speaker-routes-style specific-before-general. Endpoints: `GET /recall`, `GET /:profileId/profile`, `GET /:profileId/asks`, `POST /asks/:askId/status`, `GET /trends`.

**Other stories:** open asks = a WHERE clause over `ambient_person_asks`; weekly trends = `date_trunc('week', …)` over `ambient_person_topic_daily` (within the retention window); "topics connecting Ella and Sam" = a self-join over `ambient_person_relations` on shared `topic:*` to_refs, dated by `observed_on`. **Answer-integrity rule:** semantic/paraphrase widening (Phase 3, `RagService.search(query, 'ambient-recall', topK, {userSub, allowPublic:false})`) is reported as "possibly related" and **never folded into the exact count** — receipts stay literal.

### 5. Consent — audio-clip retention is REJECTED (with a falsifiable reopening gate)

**Verdict: do not build audio-clip retention in any phase.** TTS re-speak of verbatim transcript satisfies "play it back" (the stated minimum). Rationale in force order:

1. **Florida all-party consent (Fla. Stat. §934.03) applies to the whole pipeline, and clips raise the bar past what we can meet.** §934.03 covers interception of oral communications regardless of storage format — transcription is already in scope. The system's answer for transcription is **informed notice**: an operator-facing household-notice obligation, surfaced prominently in the ambient *enable flow* (not buried in settings), telling the owner they must inform persons present, and per-person modeling default-off until the owner affirms that notice (§3). Clips demand more: **verifiable consent from the recorded person**, and a consent ledger keyed to a voiceprint of someone we cannot authenticate is consent theatre. Notice can be attested; consent cannot.
2. **Minors** — household deployments capture children's voices; children cannot consent and diarization cannot reliably flag minor status. (This argument binds profiling too — hence the §3 `is_minor` inference-layer hard stop.)
3. **The promise is load-bearing** across all six §Context surfaces and is the trust anchor of the ambient feature. "Never stored, unless…" devalues every other privacy claim.
4. **No story needs it** — counts, quotes, timestamps, asks, trends, and re-speak all come from transcript text.

**What ships instead (Phase 2, all of it — disclosure lands with the capability, not after):**
(a) **Household notice in the enable flow** as above.
(b) **The consent ledger with real gating semantics.** `granted` is not decorative: it is the per-profile switch that turns modeling ON (§3 default-off). Method `in_app` = the person acknowledged in their own account (tenant members); `owner_attested` = the owner affirms the person was informed; `written` = out-of-band record. The asymmetry with §5.1 is deliberate and stated: owner attestation is acceptable for an *informed-notice* claim gating deletable inferences, and categorically insufficient for the *consent* claim clips would require.
(c) **Decline = stop AND purge.** A latest-status `declined` (transcript scope) halts all future enrichment/rollup/vector ingest for that profile AND deletes every already-derived row for it — enrichment rows (via its segments), asks, topic_daily, relations, and `ambient-recall` chunks. It is an opt-out, not merely a stop. The voiceprint profile itself is **retained frozen, match-only, solely so the decline keeps being honored** on future audio (stated here so nobody "cleans it up"); the owner may instead delete the profile outright, accepting that a returning voice starts a fresh default-off profile. **Voiceprint-scope declined:** centroid accretion stops (observation writes for that profile are skipped) and the embedding is frozen match-only; merge targets and assignment moves involving a declined profile carry the decline with them.
(d) **Disclosure rewrite on all six surfaces** (panel `jarvis-ambient.js:270`, `README.md:190`/`:217`, `site/oswarm.ai/index.html:1372`, `docs/architecture/jarvis-architecture-and-flow.md:404`, and the pinning test `tests/unit/jarvis-ambient-client.spec.ts:77` updated in the same commit). The copy must disclose, concretely: derived per-person inferences (topics, tone/intent, asks, presence) are stored as **deletable inferences**; they cover **non-user voices**; how a heard person is excluded (decline) and that exclusion purges history; and the retention bound. "Only transcript text and encrypted voice profiles you choose to remember are kept" becomes false the day Phase 2 ships and must not survive it. This is a mode change and is labeled as one.
(e) **Explicit rejection of voice cloning** — playback never synthesizes a heard person's own voice.

**Reopening gate — ALL must hold before an ADR proposing clips may be drafted:** (a) session-level all-party consent: one unconsented or undiarized voice in a `session_id` ⇒ no clips for that session, with an enrolled-speakers-only mode that discards unconsented voices pre-storage; (b) consent captured out-of-band per person via a real user-account acknowledgment (never inferred from a voiceprint, never owner-attested), ledgered under a new `audio_clip` scope added by the successor migration, with revocation-triggered hard delete; (c) minors hard-blocked — no guardian-grant mechanism exists or will be pre-built; (d) retention bounded by `expires_at` ≤ `transcript_retention_days` with a purge sweep; (e) clips AES-256-GCM encrypted with the per-owner HKDF pattern from `speaker-embedding-crypto.ts` (new info string `'oshal-audio-clip-v1'`); (f) a visibly different UI mode (distinct mic badge + forced re-acknowledgement, not a buried toggle); (g) all disclosure surfaces rewritten and a data-lifecycle exporter for the clip store shipped **before** code.

## Phased plan (each phase independently useful)

**Phase 1 — Ella recall (no new engines, no new bots, no LLM enrichment).** Shipped as the Ambient Recall extension app: person-model schema bootstrap (FTS column + tables + append-only trigger), `src/features/person-model/` slice (guard matcher + receipts + `recallQuery`), `/api/jarvis/ambient/person` routes, `swarm-apps/person-model.yaml`, and `/api/jarvis/ambient/person/` surface with browser TTS re-speak. The in-Jarvis natural-language hook is deferred until `jarvis-routes.ts` is decomposed below the hard file cap.
*Done when:* from localhost with `MOCK_OIDC=true`, the Ella query returns count + quoted lines + timestamps and re-speaks a line; cost row appears in `chat_tasks` (Jarvis agentId); new tables appear in `/api/me` export; deleting a transcript day cascades the FK-bearing tables (`ambient_utterance_enrichment`, `ambient_person_asks`, `ambient_person_relations`) and `ambient_person_topic_daily` converges after the rollup pass; `npx tsc --noEmit` clean.

**Phase 2 — Enrichment + asks + consent ledger + disclosure.** `ambient-analyst` Form B bot (both registries + persona + ADR-083 selector fields, boot passes `validatePersonaIdentities()`), micro-batch runtime with the recorded ADR-036 deviation + kill switch, nightly pure-SQL pass (rollups, retention purge, reconciliation), taxonomy CHECKs, ask/commitment extraction with provenance columns, consent ledger + per-profile default-off gating + decline purge + `is_minor` inference stop, `RETAINED_DISCOVERED_TABLES` entry, jarvis-speakers consent UI, recall-guard dispatch to ambient-analyst, and the full six-surface disclosure rewrite (pinning test updated same commit).
*Done when:* "what has Ella asked me that I haven't followed up on" answers with open asks rendered beside verbatim source quotes; marking done provably survives an enrichment replay (dedupe_key test); a `declined` profile stops accreting AND a test verifies person-model queries about it return nothing derived; a profile never affirmed as informed accrues nothing; topic_daily rows older than `transcript_retention_days` are purged (retention test); all six disclosure surfaces carry the new copy and the pinned test passes; a day of enrichment for one owner costs a bounded, logged amount in `chat_tasks` under ambient-analyst.

**Phase 3 — Semantic recall + trends + drift proof.** **Entry gates, before any ingest:** (1) the ingest path populates the `rag_chunks.owner_sub` column (and `tenant_id` where applicable) and a test proves `/api/me` delete removes the rows; (2) chunk-purge hooks are wired into all four segment-delete paths plus the decline purge; (3) ingest is gated on `pgvectorRagEngine.isAvailable()` — on deployments where migration 070 skipped or `RAG_ENGINE≠pgvector`, the semantic leg is silently absent and recall remains FTS-exact-only (§4's permanent exact leg). Then: `ambient-recall` chunks with deterministic `pm:<segment_id>` ids via `PgvectorRagEngine.addChunks` (barrel export added), trend + relationship query paths, `scripts/person-model-rebuild.ts`, `person_model_projections` written by the nightly job.
*Done when:* a paraphrase query ("the ball sport Ella likes") surfaces volleyball lines marked "possibly related" without changing the exact count; weekly-trend and topics-connecting-two-people queries answer from SQL; deleting a transcript day provably removes its `ambient-recall` chunks and a full `/api/me` delete leaves zero rows for that sub in `rag_chunks`; rebuild run twice yields identical row counts and zero duplicate chunks; the ledger shows matching counts after a from-scratch rebuild.

**Phase 4 — Person profile surface + governance closure.** Person pages as tabs (Topics / Asks / Presence / Consent) extending `jarvis-speakers.js`; delete/rename/merge re-projection hooks verified end-to-end; this ADR indexed in `docs/adr/README.md`; optional prosody tone via the sidecar (same column, different `model`).
*Done when:* a human browses a person profile from localhost; deleting a profile leaves zero derived rows for it; `node scripts/docs-link-check.js` passes.

## Non-goals / rejected alternatives

- **Four-engine temporal-KG composition (rejected lens).** Its mechanics were the best in the field — deterministic chunk ids, the drift ledger, reified graph events are all grafted here — but it parked owner-private rows on the ADR-076-exempt superuser tsdb (violating "RLS on new tables") and spent four engines plus three projection pipelines on ≤2-hop household-conversation questions.
- **Adopting the Arango person graph now.** Every stated relationship story is 2-hop SQL over `ambient_person_relations`; ADR-045's own rule forbids forcing graph where relational fits. Deferred behind the §1 escalation trigger, with the sanctioned projection shape pre-recorded.
- **A `person-model-enrich` ticketType now.** Ticket types register only via built-in `WORKFLOW_PIPELINES` or a swarm-app manifest; this design adds neither (§6), so the name is reserved and the micro-batch deviation is recorded instead — no ticket that the dispatcher would defer forever.
- **The `AppRoute` delegate path** — dead code (`orchestrate()` has zero call sites); routing uses the recall guard + ADR-083 call-out only.
- **Building clip retention as a consent-gated mode.** Rejected per §5; the session-level gate, minor exclusion, and visible-mode UI are preserved as the reopening gate's spec, not built — and its enum values (`audio_clip`, guardian grants) are deliberately absent from migration 088.
- **TimescaleDB, ChromaDB, the ADR-066 `personal-graph` slice** — §1.
- **A Form A container bot** — ambient-analyst is reason-only; Form B per `docs/building-a-bot.md`.
- **A new swarm-app manifest** — ADR-097 who-is-it-for test.
- **Voice cloning for playback** — exceeds any collectible consent; rejected outright, not deferred.
- **Per-segment real-time LLM enrichment** — cost with no story it serves; micro-batches lose nothing.
- **`RagService.ingest` for projection writes** — timestamped chunk ids duplicate on replay; deterministic ids via `addChunks` are what make rebuild safe.

## Consequences

### Positive
- Every Person Model query answers from one database; the single derived index carries an accounting ledger and explicit deletion parity; rebuild-from-canon is a pure-SQL script, not a reconciliation subsystem.
- Export/delete works from Phase 1 for all relational stores via structural discovery, and Phase 3's entry gates extend that guarantee to the vector store before it exists — no store ever ships ahead of its delete path.
- "Raw audio is never stored" stays literally true on every surface; heard non-users gain a real opt-out — decline stops *and purges* — and modeling is per-person opt-in (default-off) rather than consent-absent.
- Phase 1 ships the hero query with zero new registry entries, engines, or containers.

### Negative (accepted)
- **ADR-036 transport deviation:** recurring micro-batch enrichment runs on the direct `executeBotOrInline` path instead of a ticketType + workflow, because no manifest or built-in pipeline registers one (§3 records rationale and compensating controls: intact cost capture, bounded batches, kill switch, harmless retry). Revisited if an ambient manifest ever ships.
- Vector-store isolation at the database level is app-level-filter-only until the Phase-3 entry gate lands the `owner_sub` column population; the engine pool's GUC bypass remains a platform-wide hardening item.
- No acoustic prosody in v1 — text-level tone only, labeled as inference everywhere it renders.
- No true audio playback — TTS re-speak is the ceiling until the §5 gate is ever met.
- Trend history is bounded to `transcript_retention_days` — long-horizon trend questions trade away deliberately for bounded retention.
- Relationship queries beyond 2 hops are not supported until the graph escalation trigger fires.
- Modeling of minors is fully disabled (inference-layer hard stop), even where a household might want it — the safe default is not configurable in this ADR.
