# ADR-101: The Browser Swarm — a fleet plane over browser-control worker nodes

**Status:** Proposed — design accepted, nothing built.

## Context

Today OSHAL has a single browser-control worker. `apply-operator` (`cb…003`) and its sibling `linkedin-profile-operator` (`cb…004`) run on the operator's own desktop as an `@oshal/chat` remote-client, driving the operator's foreground logged-in Chrome via OS-level input (`apply-operator-mcp` `browser_control` tools + `codex.exec`, screenshot-driven, never CDP/Playwright/JS injection). Dispatch is a one-desktop, one-worker rail: `pickApplyClient()` (`src/app/apply-dispatch.ts`) selects a *single* box, `dispatchApply()` enqueues one `codex.exec` envelope via `remoteClientRegistry.enqueueTask`, a 30-min `applyInFlight` watchdog catches a crash, and the box POSTs its outcome back to the service-secret `POST /api/apply/ingest`.

ADR-099 proved the generalization we need: any device is a registered swarm node, and `DroneService`/`DroneFleet` is the id→node fleet plane (embedded default `alpha` + remote nodes joining by authenticated heartbeat; offline nodes reject at command time; per-node routes with a back-compat default). The browser swarm applies that pattern to browser-control workers: N machines, each on a browser the runner is signed into, applying/researching/form-filling in parallel on the operator's **own consented** accounts — with session/login affinity, a durable sharded queue, retries, recipe replay, human handoff on any checkpoint, and the existing approval gate on every outward write.

## Decision

Promote the apply rail to a **fleet plane** over browser-control worker nodes, reusing every existing rail and adding **no new transport** (the affinity index + sharding assignment loop are net-new orchestration — see Phases).

### 1. Fleet plane — id→node, a projection not a second registry

**`BrowserFleetService` (NEW)** — `src/features/browser-swarm/services/browser-fleet-service.ts`, mirroring `DroneService`. It is a **pure projection over `remoteClientRegistry.listClients()`** (the shared in-process `RemoteClientRegistryService`), **never a parallel `Map`** — liveness stays strictly heartbeat-derived there (no split-brain). A node is "in the browser fleet" iff `status==='online' && healthy`, its capabilities include `codex.exec`/`shell.exec` **and** the `browser_control` MCP namespace (the `apply-operator-mcp` presence is the real in-fleet gate). Constants mirror the drone fleet: `NODE_STALE_MS=15_000`, `MAX_FLEET_SIZE=32`, `NODE_ID_RE=/^[a-z0-9][a-z0-9_-]{0,31}$/i`.

- `listFleet(): BrowserNodeSummary[]` — `{ nodeId, ownerSub, online, capabilities, ownedLogins[], queueDepth, activeTaskId, lastSeenMs }`, sorted by nodeId.
- `getState(nodeId = DEFAULT_NODE_ID)` — `DEFAULT_NODE_ID = 'desktop'` is a **selection label only**, not a guaranteed-present embedded node. Unlike drone's `alpha` (a real in-process `SimDroneProvider`), there is no embedded browser node: `getState('desktop')` and the legacy `POST /submit` path fall through to `pickNode`'s online-worker selection and return the existing **503 worker-offline** when the fleet is empty.
- `pickNode(opts): RemoteClientRecord | null` — the multi-node generalization of `pickApplyClient` (§2). **`pickApplyClient` is kept and re-implemented as `pickNode({affinityKey:'default'})`**. Only `profile-studio-dispatch.ts` (the sole direct importer of `pickApplyClient`, line 29) changes one import; **`apply-submit.ts` is untouched** — it consumes `dispatchApply`, which retains `pickApplyClient` internally. Offline/unknown nodes reject here; never throws.

**Per-node routes with a back-compat default (NEW)** — `src/app/routes/browser-swarm-routes.ts`, `createBrowserSwarmRoutes(ctx)`, mounted `app.use('/api/browser-swarm', serviceSecretOr(requiresAuth), …)`, mirroring `drone-routes.ts` `registerCommands('')` + `registerCommands('/fleet/:nodeId')`:

- `POST /submit` — legacy single-worker path → `DEFAULT_NODE_ID` selection (behaviourally identical to `/api/apply-operator/submit`).
- `POST /fleet/:nodeId/submit` — target a specific node; `nodeId = req.params.nodeId || req.body?.nodeId || DEFAULT_NODE_ID`.
- `POST /batch` — the sharded bulk entry point (§3).
- `GET /fleet`, `GET /fleet/:nodeId/state`, `GET /fleet/:nodeId/tasks`.
- `POST /affinity` — node-identity affinity ingest; **requires `hasValidServiceSecret(req)` (401 for OIDC sessions)**, the drone `POST /nodes/heartbeat` "a NODE identity, never an operator browser" pattern.
- Outcome callback stays the existing service-secret `POST /api/apply/ingest` — **no new ingest surface**.

### 2. Node runtime — the existing companion, plus affinity

**No new runtime binary.** A browser node **is** an `@oshal/chat` remote-client (`RemoteClientService`), joined via the standard installer (`install-node.ps1 -JoinCode OSJOIN1.…`). It already registers, heartbeats (10 s), polls `GET /:clientId/tasks/next` (2.5 s), and executes `mcp.call-tool` intents. `apply-operator-mcp` supplies `browser_control` (`preflight, shot, click, type_text, paste, key, nav, upload, pick_place`); oshal-chat's allowlisted local-tools MCP supplies `codex.exec`. Reasoning runs `codex-cli`/`gpt-5.5` (vision) — **OS-input only, screenshot-driven, never CDP/JS injection**. Satisfies "shells out ⇒ Form A codex-cli node."

**Registry identities (NEW).** Register a `browser-worker` family (`cb000000-…-000000000010+`) and a **`browser-operator`** Form-B concierge (drafts-only) in **both** `swarm-bot-registry.ts` and `swarm-bot-registry-local.ts`, `harnessType: codex-cli`/`apiType: openai-codex` (workers), `accessRoles: ['operator','swarm']`. Registry identity only, **no compose service**; BYOK on the mounted `~/.codex` login, no vendor key. **In the same change, fix the pre-existing half-satisfied rule:** add `apply-operator` (`cb…003`) and `linkedin-profile-operator` (`cb…004`) to the local registry, where they are currently missing.

**Session/login affinity — the net-new mechanism.** A browser node's real constraint is *which sites its foreground Chrome is signed into*. The node reports this via a **live login-probe** — nav to a site's `/me`-style URL, `shot`, reason "signed in? y/n", **never reading cookies or entering anything** — POSTed as booleans to `POST /api/browser-swarm/affinity`. `BrowserFleetService` indexes `ownedLogins[]` per node. `pickNode({affinityKey})` order generalizes `pickApplyClient`:
1. explicit `nodeId` (operator override);
2. **affinity match** — online node whose `ownedLogins` contains `affinityKey`, least-loaded by `queueDepth`;
3. `APPLY_EDGE_CLIENT_ID`/`tailnetHostname` pins (legacy);
4. for a non-login-gated flow, any online worker.

**Affinity is a preference, not a lock.** For a login-gated flow with no affine node online, the task **defers** with a `[MORNING: log into <site> on <node>]` note — it does **not** fall through to a node it isn't authenticated on (which only burns a run hitting the STOP wall). Affinity is sticky per login: the LinkedIn-owning box gets the LinkedIn apply *and* the LinkedIn profile edit, serialized on one browser.

**Isolation.** Each node is a distinct machine with its own foreground Chrome, sticky `ownerSub`, and read-only `~/.codex`. Nodes share nothing at runtime. `requireDeviceAccess` gates every `/:clientId` surface to owner-or-operator (unowned = operator-only, fail-closed); scoped per-task workspace sync (`resolveHeldWorkspace`) hands a node only the folder for a task it currently holds. **`email_code` retrieval always resolves the Gmail connector token for the *task's* `userSub` (the person applying), never the node's `ownerSub`** — a node never reads a Gmail it wasn't handed a token for, so a task executing on runner Bob's box still reads only the applicant's own inbox codes.

### 3. Task model & scheduling

**Envelope:** unchanged `A2ATaskEnvelope`, `intent:'mcp.call-tool'`, `input:{name:'codex.exec', arguments:{prompt, sandbox:'danger-full-access'}}`, enqueued via `remoteClientRegistry.enqueueTask`. Prompt built server-side (`buildApplyPrompt` generalized), injecting `SWARM_SERVICE_SECRET` + callback.

**Durable queue + idempotency — `browser_swarm_task` (NEW, migration `088-browser-swarm.sql`; max on disk is 087 — NOTE: ADR-100 also claims `088` for its person-model migration; both are design-only, so whichever ships first takes 088 and the other takes the next free number).** RLS `user_sub`-scoped (`runWithRequestIdentity`): `task_id UUID PK, user_sub, batch_id, affinity_key VARCHAR(64), flow VARCHAR(32), target_ref VARCHAR(128), idempotency_key VARCHAR(200) UNIQUE, assigned_node, dispatch_task_id, attempts INT, submit_state VARCHAR(16) (unknown|submitted|not_submitted), status VARCHAR(24) (queued|assigned|in_flight|assist_review|deferred|applied|dismissed|failed), recipe_id UUID NULL, created_at, updated_at`. Wired into `080-data-lifecycle.sql` export/delete (ADR-036).

**Three dedupe rails.** `idempotency_key = sha256(user_sub | flow | target_ref)`; enqueue is `INSERT … ON CONFLICT (idempotency_key) DO NOTHING` (restart-durable, blocks re-**insert** of the same job). This layers on `oshal-apply.js queue claim <id>` and the in-memory `applyInFlight` Map. **Scope of the guarantee:** the idempotency key blocks a duplicate *row*, not a re-*dispatch* of an existing row (a retry is an UPDATE). No-double-submit therefore holds **structurally only for ASSIST families** (a human re-reviews the filled form). For a **proven-clean auto-submit family**, a crash *after* Submit but *before* the ingest POST would otherwise re-dispatch and re-submit — so a retry of a row last seen `in_flight` against an auto-submit family is forced to **`assist_review`** (human confirms whether the prior Submit landed), or is held until ingest supplies a positive `submit_state`. Blind auto-resubmit is disallowed.

**Sharding a bulk job.** `POST /batch { userSub, postingIds[], confirm:true }` mints `batch_id`, inserts N rows (`ON CONFLICT DO NOTHING`), each tagged with its ATS `affinity_key`. A **single-pass assignment loop** (Phase 1) pulls `queued` rows, groups by `affinity_key`, and per online node computes **available slots = 1 − in-flight** (browser reality: **per-node concurrency = 1**, one foreground Chrome). It assigns at most one affinity-matched task per free node via the existing rail: claim → `buildApplyPrompt` (ASSIST) → **fail-closed `browser_command_log` `attempt` row (§4)** → `dispatchApply` → arm the 30-min watchdog; set `status='in_flight'`, `assigned_node`, `dispatch_task_id`. Each node fills everything, **STOPs before final Submit** unless the `(site,family)` is proven-clean, POSTs `/api/apply/ingest`. Ingest clears the watchdog, records the outcome, sets the row terminal, and **frees the slot** → next pass pulls the next band. **Backpressure is intrinsic** — `queued` rows wait when every single-slot node is busy; `MAX_FLEET_SIZE=32` caps fan-out. Phase 2 promotes this pass into a durable recurring `browser-swarm-scheduler.ts` tick with cooldowns.

**Retries.** A `failed`/`deferred` row with `attempts < 3` returns to `queued` on the next pass (idempotency key ⇒ no duplicate row; auto-submit `in_flight` rows go to `assist_review` per above). `deferred` (CAPTCHA/2FA/parser) requeues behind a cooldown for **human handoff**, not blind retry, and may retry on a *different* affine node.

**Recipe capture/replay (additive, Phase 3).** Promote the `apply_trace` learning trace to `browser_recipe` (`recipe_id, affinity_key, flow, steps JSONB, proven_clean BOOL`). Replay hands the node `recipe_id`; it replays the deterministic step sequence, falling back to screenshot-reasoning when an expected-shot check fails — cutting LLM cost. **Auto-submit promotion is graduated and revocable:** `proven_clean` upgrades a `(site,family)` from assist to auto-submit; setting `proven_clean=false` **reverts to assist within one run**; auto-submitted writes still audit; standing "auto-apply matching my template" rules are template-scoped. Replay never changes the STOP/ASSIST gates. `browser_recipe.steps` can hold typed form values (name/phone/employment answers), so it is **wired into `080-data-lifecycle` export/delete** (PII redacted from `steps` or scoped by `user_sub`).

**Human-in-the-loop STOP protocol (reused verbatim).** A login page, checkpoint, CAPTCHA, phone/device 2FA, export-control attestation, broken parser, or >~8 stuck steps ⇒ the node **never enters credentials or codes**, parks, and reports `deferred` with a `[MORNING: …]` note. `assist_review` waits for the human's Submit in the Approvals surface.

### 4. Approval, audit & cost

**Two write classes, and what actually gates each.**
- **Connector-declared writes** (a profile/status update or checkout-prep write with a real API) route through the single pipeline `runConnectorAction` (`action-executor.ts`) **verbatim**: validate params → approval gate (`connectorActionRequiresApproval` — medium/high risk or `approvalRequired` ⇒ HTTP **428 `confirmation_required`** unless `hasExplicitWriteConfirmation(body)`) → lazy broker-only caller-owned creds → **fail-closed pre-write `attempt` audit row** (refuse **503** if audit unavailable) → HTTP (retries off) → terminal row.
- **Browser-driven writes with no API** (LinkedIn edit, ATS Submit — the majority path) **cannot cross `runConnectorAction`** — there is no connector action and no HTTP call to audit-before. This ADR does **not** claim full 428 reuse for them. The accepted substitute is: the **ASSIST-mode STOP rail** (fill-but-don't-Submit; auto-Submit only for proven-clean families) **plus** the `/batch` and `/submit` routes calling `hasExplicitWriteConfirmation(req.body)` and returning `confirmationRequiredPayload('browser-swarm', flow)` 428 when absent — so the *batch authorization* crosses the fail-closed check, and each *individual* submit still needs a proven-clean flag or a human click. **To recover the connector rail's audit-before-write property**, the per-submit `browser_command_log` `attempt` row (below) is written **fail-closed**: an auto-Submit dispatch is **refused if that insert fails**, mirroring `executeAuditedWrite`'s 503 — so an auto-submitted browser write with zero persistent record is impossible.

**Remote approve.** `NotificationRouter.notify(userSub, 'browser-swarm', msg)` (email default; BYO Twilio/Telegram) is **push-only** — a texted "yes" **never** satisfies `confirm:true`. Approval is always an authenticated `confirm:true` API click in the Approvals surface. The chat-channels Telegram webhook is *not* wired to confirm writes.

**Audit.** Add **`browser_command_log` (NEW)**: `log_id UUID PK, user_sub, node_client_id, site, command VARCHAR(32), detail JSONB, outcome VARCHAR(16) (ok|rejected|deferred), created_at`. It **carries RLS `user_sub` policy** in migration 088 (it holds per-user activity; this diverges deliberately from `drone_command_log`, which is unpolicied — the browser table is more PII-adjacent). It is an **append-only audit table exempt from delete** in `080-data-lifecycle` (export yes, delete no) with a stated retention rationale, mirroring the audit-trail treatment of `connector_action_audit`. The pre-dispatch `attempt` row is fail-closed (above); the terminal `ok/rejected/deferred` row is best-effort via a `.catch`-logged-at-ERROR helper (never swallowed). Connector writes additionally hit `connector_action_audit` (`params_hash`, never raw PII).

**Cost (ADR-036) — stated plainly, not papered over.** The browser worker is reached via `remoteClientRegistry.enqueueTask` → `codex.exec` on the desktop node, **not** via `BotNodeClient.execute` → `/api/swarm-execute`. `recordCost` lives only in the bot-node path and is **not** on the remote-client rail: the node runs codex CLI under the operator's **own `~/.codex` BYOK OAuth** and posts back only `{result, note}`. **Therefore no `chat_tasks`/`oshal_cost_events` row is written today for browser-worker reasoning, and `linkTask` has nothing to roll up.** This is acceptable under ADR-036 because the spend is the operator's own subscription/OAuth, not a platform-billed model call. **Phase 2 (NEW, unbuilt) optionally closes the gap:** add a token/cost field to the `/api/apply/ingest` callback → `recordCost` under the `browser-worker` `agentId` + `ownerSub` + `linkTask` to the ticket. The controller/scheduler **never calls an LLM** — it only routes and audits.

### 5. Consent & the operator-owned boundary

This swarm drives **only** browsers on machines whose runner *knowingly joined*, on accounts the operator owns. The properties below are a mix of **structural** and **prompt/model + human-visible** guarantees, labelled honestly:

- **Consent at join (structural, but generic).** A machine becomes a node only via `install-node.ps1 -JoinCode` run by the person at that machine; `ownerSub` binds at registration and is sticky. **The generic "join a swarm" consent is not specific consent to "the operator may pilot my logged-in browser."** To close this: (a) **browser-swarm dispatch is scoped to nodes whose `ownerSub == the dispatching operator's own sub`** unless the node's runner has set an explicit per-node **`browser_pilot_consent`** flag (separate from generic join); (b) **unattended / `-OrbOnly` nodes are excluded from browser-control targeting** (or require an on-machine presence signal), because their "visible foreground activity" mitigation fails when nobody is watching; (c) the installer surfaces at join-time exactly what browser piloting means. The `apply-operator-mcp` (`browser_control`) presence is cited as the real in-fleet gate.
- **No-credential-entry is prompt-and-model + human-visible, NOT a tool-level impossibility.** `browser_control` includes `type_text(text)` and `paste(text)`, which can type *any* string, including credentials, into any focused field. The "never enter a login/2FA code, STOP on checkpoint" guarantee is enforced by the persona prompt, the reasoning model obeying it, and a human seeing the foreground screen — **not** by the absence of a login primitive. *Optional structural hardening (recommended):* a node-side guard in `apply-operator-mcp` that classifies the current screenshot and **refuses `type_text`/`paste` on a login/2FA/CAPTCHA page**, or an allowlisted field set. The existing `email_code:auto` scope reads ATS one-time codes from the applicant's **own** Gmail *post-login* — operator-owned and distinct from the never-enter-a-login-code rule.
- **Gated system tools (structural).** oshal-chat's `screen.capture`/`shell.exec`/`desktop.control` sit behind `allowSystemControl` (off by default); `runLocalTool` hard-fails an unknown tool name; the local-tools MCP is an allowlist. The browser swarm needs none of these.
- **Visible activity + full audit.** The node drives the *foreground* browser via OS input — on-screen by construction (CDP is banned). Every task/write is audited under a real `user_sub`; `GET /fleet` shows which nodes exist, who owns them, and what logins they own.
- **No raw browser link on the network (structural).** The only way to command a node is an authenticated envelope through the swarm (ADR-099) via `remoteClientRegistry.enqueueTask` under shared-secret/OIDC auth.

## Phases (each independently useful)

**Phase 1 — Parallel job-apply across ≥2 nodes, affinity + gate.** `BrowserFleetService` as a projection over `remoteClientRegistry`; `pickApplyClient` → `pickNode({affinityKey})` with login-affinity + least-loaded + defer-with-note fallback; `browser_swarm_task` + `browser_command_log` (migration 088, RLS); `POST /batch` **with the single-pass assignment loop** (one affinity-task per free node, concurrency=1/node); the fail-closed per-submit `attempt` audit row; reuse `dispatchApply`, ASSIST STOP rail, `applyInFlight` watchdog, `/api/apply/ingest`. Register `browser-worker` + `browser-operator` in **both** registries and add `cb…003/004` to the local registry. Scope dispatch to owner-consented, attended nodes (§5). This phase adds **net-new orchestration** (affinity index + sharding) on top of the existing transport — it is not "no new engine." **Done-when:** two joined, consented nodes drain a **200-posting batch in parallel** via the single-pass loop, LinkedIn-affinity honored, every submit ASSIST-gated, **no double-submits for ASSIST families (idempotency + assist-on-retry proven)**, all dispatches/outcomes in `browser_command_log`; a unit test mirrors `drone-fleet.spec.ts` (two concurrent nodes, offline-after-stale rejection); operable from localhost with `MOCK_OIDC=true`.

**Phase 2 — Durable scheduler, retries, backpressure, cost, surface.** Promote the single-pass loop into a recurring `browser-swarm-scheduler` tick; retry `attempts<3`; `deferred` cooldown; optional `/api/apply/ingest` cost field → `recordCost` under the browser-worker `agentId`; a Browser Swarm fleet/progress surface via a NEW `swarm-apps/browser-swarm.yaml` (`suite: ai-knowledge`). **Done-when:** a 200-batch runs to completion across ≥3 nodes with a live progress view; a killed node's rows escalate + retry on a survivor without duplicates (auto-submit rows go to `assist_review`); the queue shows backpressure; browser-worker spend appears in `chat_tasks` per-ticket.

**Phase 3 — Recipe capture/replay + graduated auto-submit.** `browser_recipe` (export/delete wired); capture clean runs; deterministic replay with screenshot-checkpoint fallback; `proven_clean` promotion as an **audited, revocable** operator action. **Done-when:** a proven family replays with a measured LLM-cost drop, gates unchanged, and `proven_clean=false` reverts to assist within one run.

**Phase 4 — Generalized authenticated flows.** `authed-pull` and `form-fill`/`checkout-prep`, affinity-routed + ASSIST-gated, via a dedicated `ticketType` + workflow (not borrowing `incident-rca`). **Done-when:** a scheduled pull runs on the affine node, stores to a `user_sub`-keyed store, surfaced as a view (ADR-036).

**Phase 5 — Carve to store package (ADR-085).** Per ADR-099 sequencing (rearchitect in-repo first, carve once stable): fleet/scheduler engine → kernel-skill candidate; surface + personas + routes + node config → the package. **Done-when:** it activates via `POST /api/swarm/apps/load` with zero static-array edits.

## Consequences

- **Positive.** Parallel throughput scales by nodes, not tabs; restart-durable no-double-submit **for ASSIST families** (idempotency + assist-on-retry); affinity keeps a login on one box; consent is scoped to owner-consented attended nodes. Fixes the pre-existing half-satisfied both-registries rule for `cb…003/004`.
- **Write-gate honesty.** Only **connector-declared** writes cross the unchanged `runConnectorAction`/428 pipeline per-write. **Browser-driven Submits are gated by ASSIST-STOP + a coarse batch-level 428**, not a per-write connector gate; audit-before-write parity is recovered only via the fail-closed `browser_command_log` `attempt` row (refuse-dispatch-if-audit-down). The Consequences claim is scoped accordingly — do not read it as full per-write 428 reuse.
- **Costs / risks.** A durable `browser_swarm_task` + a scheduler tick are more surface than a pure in-memory projection — accepted for correctness. Per-node concurrency=1 bounds throughput by node count. Affinity depends on the login-probe reflecting reality; a stale probe defers rather than mis-routing. The in-memory `remoteClientRegistry` dies on controller restart (nodes re-register on next heartbeat) — the durable table + watchdog are the crash/restart backstops.
- **Legal / ToS.** This design deliberately uses OS-input, foreground, non-CDP automation *because* CDP/JS injection is fingerprinted — i.e. it is built to be indistinguishable from a human at a keyboard. Bulk apply runs, LinkedIn profile edits, and Phase-4 authed pulls of sessions where "no API exists" **likely breach the ToS of LinkedIn and many ATS/sites** (no automated/scripted access, no scraping) and **risk account suspension**. This is **the operator's own-account risk, which the operator assumes**; the node-runner is warned at join. A **per-site allow/deny + rate-limit policy hook** (beyond concurrency=1) is a required control, surfaced to both operator and node-runner. The platform does not encourage circumventing any site's protections.
- **Interactions.** Extends the apply/profile rails without rewriting them (`profile-studio-dispatch.ts` one-import change; `apply-submit.ts` untouched). RLS + export-or-documented-exemption required on all new owned tables. Does not touch the ADR-085 one-app-one-package unit; `suite:` is grouping metadata only.

## Non-goals / rejected alternatives

- **No new transport.** Reused `remoteClientRegistry.enqueueTask` + `codex.exec`; rejected a bespoke browser-control HTTP endpoint (violates ADR-099 "no raw links") and a drone-node-style `browser-node-server.ts` (the oshal-chat daemon already *is* the runtime).
- **No parallel *approval* gate for API writes.** Reused `runConnectorAction`/428. For API-less browser writes, the ASSIST-STOP + batch-confirm + fail-closed command-log is the acknowledged substitute, not a claim of full pipeline reuse.
- **No reply-to-confirm.** Notification transports stay push-only; a texted "yes" never satisfies `confirm:true`.
- **No per-node concurrency >1.** One foreground Chrome per box; parallelism = N nodes, slot = 1−in-flight.
- **No headless/CDP path; no claim of a tool-level credential bar.** Login/checkpoint/CAPTCHA/2FA always STOP-and-handoff — but that is prompt/model + human-visible enforcement (optionally a node-side login-page refusal guard), not the absence of `type_text`/`paste`.
- **No second registry / no cookie-reading affinity.** `BrowserFleet` is a projection over `remoteClientRegistry`; affinity reports booleans, never cookies.
- **No edge-agent (Redis/DB-direct) rail.** Chose the sanctioned remote-client HTTP + shared-secret join.
- **Operator-owned / consented sessions ONLY.** Aggregates the operator's own logged-in sessions on owner-consented, attended machines. It is not, and must not become, a tool to watch or drive other people's devices or non-consenting accounts; dispatch is scoped to `ownerSub`-matched or explicitly-consented nodes, unattended nodes are excluded, and every task is audited under a real `user_sub`.
