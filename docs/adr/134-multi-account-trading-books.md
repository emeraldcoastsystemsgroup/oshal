# ADR-134: Multi-Account Trading Books

- **Status:** Accepted (operator mandate 2026-08-26; design passed a three-lens adversarial review — live-safety, boundary/security, requirements — whose 29 amendments are integrated below)
- **Date:** 2026-08-26
- **Depends on:** ADR-036 (bot-owned domains), ADR-052 (no justification, no trade), ADR-085/093 (kernel/store carve), ADR-095 (Strategy Library apply-to-profile), ADR-113 §4 (multi-connection connector schema), ADR-124 (unwalled report tables)
- **Supersedes in part:** the two-book `mode` axis of migrations 034/065 (retained as a column, retired as the *only* book key)

---

## Context

The trading system today is a **two-book world keyed by `mode IN ('paper','live')`**: one paper book (Alpaca, shared env keys) and one live book (Schwab, per-user OAuth token, account selected by the process-global `SCHWAB_ACCOUNT_NUMBER` env pin else first-in-enumeration — `schwab-broker-adapter.ts:307-320`). The operator requires:

1. Log into Schwab via the existing connector → **all accounts under that login pull in automatically** (no `SCHWAB_ACCOUNT_NUMBER`).
2. Add as many accounts as desired; **switch fast** between them.
3. **Per-account asset-mix editing** and **a distinct trading strategy per account**.
4. A **consolidated summary report** like Schwab's own summary page (total value, per-account values + day change, positions rollup).
5. Paper trading remains. **Single-account live trading works today and must keep working throughout the migration** — the live book trades every market morning.

What the code says (from the five coupling maps, cited throughout):

- The Schwab OAuth token is **login-scoped**: `scopes: []`, one bearer enumerates every account under the login (`connector-provider-registry.ts:251-254`); `GET /accounts/accountNumbers` is called at exactly two sites (`schwab-broker-adapter.ts:311`, `connector-account-lookup.ts:368`). Multiple Schwab connections per user are already schema-representable (`oshal_connections` partial unique `(user_sub, provider, account_key)`, `connector-tenancy.ts:115`) but **unreachable from the trading path** — the resolver registered at `oshal-applications/trading/src-routes/trading-routes.ts:101` passes no `ConnectionSelector`.
- `mode` is baked into **seven unique indexes/PKs** (schema map, `trading-schema.ts:89` finding), the orders idempotency key + submission-race arbiter (`idx_trd_orders_client_mode`, the 2026-07-08 clobber fix and 2026-08-18 twin-order fix), the autopilot `requestId` text (`trading-schedule-dispatch.ts:247`), the reconcile-ledger deterministic `decision_id` derivation (`trading-reconcile-ledger.ts:111`), the drawdown breaker PK (`trading-equity-guard.ts:27` — the "withdrawal = phantom drawdown HALT" table), and the trailing-stop peaks PK.
- Strategy binding is **one active `trading_config_overrides` row per user, book-blind** (`idx_trd_cfg_override_one_active ON (user_sub) WHERE active`, `trading-config-overrides.ts:86`), read once per fire at `trading-schedule-dispatch.ts:1365` and threaded through an already-parameterized overlay rail (`riskPolicy`/`coreConfig`/`rotationConfig`/`runAutopilot` — strategy map).
- The route surface, `trading.html`, and the strategy-lab apply flow live in the **store repo** (`c:/Projects/oshal-applications/trading`) with compiled `.js` twins; store deploys are `docker cp → deployed-apps + api restart`, not git merge (surfaces map). Engine, schema, stores, dispatch loops, and broker binding are **core** (ADR-085 "only the surface carves").

**Seed deviations (with evidence):**

- **No `strategy_id` column on the books table.** The seed proposed it; the strategy map shows the fire-time rail is the `trading_config_overrides` *snapshot* (apply copies config; later strategy edits deliberately do not change the live override — `trading-strategy-lab-routes.ts:516-518`). A live pointer on the book row would create a second precedence source and break ADR-095's snapshot semantics. Per-book strategy = the override table re-keyed per book (D4).
- **No flag-gated `requestId` format.** Instead, books carry a stable `ref` where the legacy books' refs are literally `'paper'` and `'live'`, so legacy id text (`auto-paper-…`, `auto-live-…`, `reconcile:live:…`) is **byte-identical** before and after the change with no format branch (D3.6).
- **No in-place unique-index swap in PR1.** The book-scoped unique indexes are created *alongside* the retained mode-scoped ones (they coexist safely while the mode↔book bijection holds), plus a DB trigger that derives `book_id` for any straggler writer. This makes `oshal-deploy.sh` auto-rollback to the previous image safe at every stage before cutover — the old code's `ON CONFLICT (user_sub, mode, …)` targets still resolve. Old indexes and PKs are retired only in PR4 (D2.3, Migration plan).
- **Auxiliary legs stay single-book.** swing/research/fast are paper-only and hard-refuse live (`trading-swing-dispatch.ts:110`, `trading-research-dispatch.ts:156`), and swing's `requestId` carries no book (engine map flag). They, plus assess/review/optimize, are pinned to the legacy paper book in this ADR; per-book learning is an explicit follow-up.

## Decision

### D1. The book model — two new core tables

Both tables are added to `ensureTradingSchema`-style self-heal bootstraps (new modules `src/app/trading-accounts-store.ts`, `src/app/trading-books-store.ts`) **and** a numbered migration `scripts/migrations/NNN-trading-books.sql` (NNN = next free number), per the dual-rail convergence rule (schema map, `trading-schema.ts:29` finding). RLS is appended at the DDL chokepoint via `buildOwnerRlsPolicyStatements(table,'user_sub')` (the peaks/equity-guard A1.2 pattern) and mirrored in the migration.

```sql
-- Discovered broker accounts (populated only by the deterministic discovery op, D5).
CREATE TABLE IF NOT EXISTS oshal_trading_accounts (
  account_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_sub       TEXT NOT NULL,
  broker         TEXT NOT NULL CHECK (broker IN ('schwab','alpaca')),
  connection_key TEXT NOT NULL DEFAULT 'default',   -- oshal_connections.account_key of the LOGIN that enumerated it
  account_number_enc TEXT NOT NULL,  -- ENCRYPTED (per-user DEK envelope via connector-token-crypto encryptToken):
                                     -- a full brokerage number is GLBA-class NPI, and bot nodes connect as Postgres
                                     -- SUPERUSER (RLS-exempt) — plaintext at rest is the bot-injection audit's
                                     -- escalation prize. Decrypt at point of use (discovery match, adapter binding) only.
  account_digest TEXT NOT NULL,      -- HMAC-SHA256(SESSION_SECRET, user_sub||':'||account_number) hex — the
                                     -- deterministic identity for the unique index (AES-GCM ciphertext is not).
  account_last4  TEXT NOT NULL,      -- plaintext display suffix; every route response returns masked forms ONLY
  account_hash   TEXT,                              -- Schwab hashValue cache; refreshed on every discovery
  account_type   TEXT,                              -- e.g. CASH / MARGIN from GET /accounts
  nickname       TEXT,
  discovered_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_seen_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_trd_accounts_identity
  ON oshal_trading_accounts (user_sub, broker, account_digest);
-- Non-partial pair uniqueness so the books FK below can be COMPOSITE — the DB-level wall against
-- binding a book to another user's account (FK validation bypasses RLS on the referenced table).
CREATE UNIQUE INDEX IF NOT EXISTS idx_trd_accounts_owner_pair
  ON oshal_trading_accounts (user_sub, account_id);

-- Trading books: the unit every ledger row, schedule, guard, and strategy binds to.
CREATE TABLE IF NOT EXISTS oshal_trading_books (
  book_id         UUID PRIMARY KEY,                 -- legacy rows use a DETERMINISTIC id (see backfill)
  user_sub        TEXT NOT NULL,
  ref             TEXT NOT NULL,                    -- short stable ref used in requestId / decision_id text;
                                                    -- legacy books: 'paper' / 'live'; new books: 'b-' || first 8 hex of book_id
  label           TEXT NOT NULL,
  kind            TEXT NOT NULL CHECK (kind IN ('paper','live')),  -- doubles as the legacy mode alias
  broker          TEXT CHECK (broker IN ('schwab','alpaca')),      -- NULL = legacy env resolution via providerFor(kind)
  account_id      UUID,                             -- NULL = legacy binding (env pin / first account), today's behavior.
                                                    -- IMMUTABLE once the book has any ledger/HWM row: re-pointing a book
                                                    -- carries the old account's high-water mark onto the new account and
                                                    -- silently trips (or launders) the drawdown breaker — a different
                                                    -- account is a NEW book, fresh HWM baseline by construction.
  enabled         BOOLEAN NOT NULL DEFAULT true,
  learn           BOOLEAN NOT NULL DEFAULT false,   -- exactly one learning book writes oshal_trading_signal_weights (D4.4)
  capital_cap_usd NUMERIC(18,2),                    -- per-book live cap; effective cap = LEAST(env, book) (D3.5)
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK (account_id IS NULL OR broker IS NOT NULL),
  -- COMPOSITE FK: a cross-user account reference fails in the database, not just in route code.
  FOREIGN KEY (user_sub, account_id) REFERENCES oshal_trading_accounts (user_sub, account_id)
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_trd_books_ref  ON oshal_trading_books (user_sub, ref);
CREATE UNIQUE INDEX IF NOT EXISTS idx_trd_books_acct ON oshal_trading_books (user_sub, account_id) WHERE account_id IS NOT NULL;
-- The single-learning-book rule is a DB invariant, not a code-path promise.
CREATE UNIQUE INDEX IF NOT EXISTS idx_trd_books_learn ON oshal_trading_books (user_sub) WHERE learn;
```

**Legacy book identity is deterministic** so backfill is idempotent across both schema rails and every boot:

```
legacy book_id := md5('oshal-book:' || user_sub || ':' || kind)::uuid
```

Backfill mints the two legacy books for every `user_sub` seen in the trading tables (paper always, `learn=true`; live only where live rows exist), `ON CONFLICT (book_id) DO NOTHING` — the deterministic PK is the **single** upsert arbiter (a two-arbiter upsert can raise `unique_violation` on the PK when the boot self-heal races the numbered migration; the idempotence spec covers a CONCURRENT double-run). A core helper `ensureLegacyBooks(pool, sub)` lazily mints them for brand-new users at first route/fire touch.

**Book lifecycle invariants are enforced in the core books store, not in route code** (any other writer — compiled-twin drift, a future surface — meets the same wall): `createBook()` hardcodes `enabled=false` for `kind='live'` (arming is an explicit operator action) and verifies account ownership in-transaction (`SELECT 1 FROM oshal_trading_accounts WHERE account_id=$1 AND user_sub=$2`, refuse otherwise — belt to the composite FK's braces); `deleteBook()` refuses in-transaction while the book has ledger rows, HWM/peaks rows, **or open venue positions** (a drawdown-halted book must never be deleted and re-created to launder a fresh HWM baseline past the breaker); `updateBook()` refuses `account_id` changes once any ledger/HWM row exists. The legitimate re-baseline case gets an explicit confirm-gated **reset-breaker** operator action, journaled to the strategy journal with `book_ref`.

### D2. The `book_id` additive migration — complete table inventory

Rules applied to every table below: `book_id UUID` is **added nullable** (`ADD COLUMN IF NOT EXISTS`), **backfilled** from the legacy derivation (`UPDATE t SET book_id = md5('oshal-book:'||user_sub||':'||mode)::uuid WHERE book_id IS NULL`), and the **`mode` column is retained and always written** (`mode = book.kind`) so the four inline `CHECK (mode IN ('paper','live'))` constraints, every existing read, and the host scripts keep working. The `requirements[]` array in `trading-schema.ts` gains every new column (validate-only deploys must assert them — schema map caveat 5).

**D2.3 Mixed-version safety trigger (PR1, dropped in PR4).** Because the store package deploys by `docker cp`, not git merge, there is a window where old store-route SQL (`trading-routes-algo-builders.ts:46/50/75/85`, `order-flow-builders.ts:91`) inserts without `book_id`. A `BEFORE INSERT` trigger on signals/decisions/orders/predictions and the five side-stores fills `NEW.book_id := md5('oshal-book:'||NEW.user_sub||':'||NEW.mode)::uuid` when NULL (skipped when `user_sub` is NULL). ### D3. Engine, adapter, dispatch, schedule, and guard changes (core)

1. **`TradingBook` type** in `src/features/trading/services/broker-adapter.ts` (beside `TradingMode`, line 39): `{ bookId, ref, kind: TradingMode, broker: 'schwab'|'alpaca'|null, accountNumber: string|null, connectionKey: string|null, capitalCapUsd: number|null, learn: boolean, enabled: boolean }`. Store-function signatures (`savePeaks`, `evaluateEquityGuard`, `recordDailyEquity`, `saveLastRotated`, `recordGateBlocks`, `recordOrder`, `placeDecisionOrder`) gain the book; they keep writing `mode = book.kind` alongside `book_id`.
2. **Broker factory** (`broker-provider.ts:83-147`): `constructAdapter(mode, sub, binding?)` — `binding` optional; absent/`account_id NULL` books construct exactly today's adapter (byte-identical legacy path). **While `multiAccountEnabled()` is false, `constructAdapter` ignores the binding entirely** — legacy env resolution, today's bytes. (Without this, discovery's legacy-book link would silently switch the live execution path from env-pin/first to exact-match-fail-closed *during* the PR1–PR3 "behavior-identical" window — a live-path behavior change shipped outside the flag. A flag-off parity spec pins it: legacy live book WITH `account_id` set, flag false → adapter construction identical to today's env path.) `buildSchwabAdapter` passes `binding.accountNumber` + `binding.connectionKey`; still refuses paper; `getBrokerAdapter` keeps the `TRADING_LIVE_ENABLED` gate and `getBrokerReader` keeps bypassing it (reconcile-while-halted property preserved — engine map). `BrokerTokenResolver` (line 50) gains an optional third `connectionKey` param; `resolveSchwabToken` threads it to `SchwabMarketData` (`market-data-source.ts:67`) so data and execution ride the same connection per book. **Fail-closed resolver guard:** constructing a Schwab adapter for a bound book while no `connectionKey`-capable resolver is registered **throws** (the fire skips) — never resolve a default token against a bound account (the store-registered resolver deploys by `docker cp`, and binding correctness must not depend on deploy ordering).
3. **Schwab adapter** (`schwab-broker-adapter.ts`): constructor stores `boundAccountNumber`. `accountHash()` (`:307-320`): when bound → exact match in the `GET /accounts/accountNumbers` enumeration, **throw if absent (fail-closed — the fire skips, per the `:1127-1139` doctrine; never fall through to first-account)**; when unbound → today's env-pin/first behavior unchanged. `ACCOUNT_HASH_CACHE` re-keyed `${userSub}:${boundAccountNumber ?? 'default'}` (`:50` — connector map hazard). Numbers stay masked in returns/logs (`:317/:433`).
4. **`placeDecisionOrder`** (`trading-engine.ts:356`) signature: `(pool, sub, book, decisionId, requestId, confirm)`. The live gate condition and its `403 live_blocked` string are **byte-unchanged** (`book.kind === 'live'`); `tests/unit/risky-write-guards.spec.ts` and the store package's `tests/trading-surface-live-gate.spec.ts` must pass untouched. **The decision SELECT gains `AND book_id=$n`** — with two live books an unscoped lookup resolves book A's decision while executing on book B, silently breaking ADR-052's justification chain; book B executing book A's `decision_id` must `404 decision_not_found` (covered in `trading-book-idempotency.spec.ts`). All ~10 call sites (routes trigger, 8 dispatch loops, reconcile) updated in PR1.
5. **Dispatch** (`trading-schedule-dispatch.ts`): `dispatchTradingSchedule` (`:1357`) resolves the book first, with three hard rules:
   - `taskData.bookId` absent → legacy book from `taskData.mode` via `ensureLegacyBooks` (the **existing out-of-band live schedule keeps working unmodified**).
   - `taskData.bookId` present but `loadBook` returns null (book deleted, or a trigger-minted id with no books row) → **skip the fire + ERROR log, never fall back to the legacy book** — the natural fallback silently trades the WRONG Schwab account from a stale per-book schedule. `loadBook` SQL is keyed `WHERE user_sub=$1 AND book_id=$2` — background dispatch runs under `runWithSystemIdentity` (`is_operator=on`), so RLS does not scope the read and **the WHERE clause is the only wall** (the token-broker SQL-scope guard precedent).
   - `taskData.bookId` present while `multiAccountEnabled()` is false → **hard-skip as a logged no-op unless it resolves to a legacy book** — flag-off must never convert per-book schedules into N duplicate dispatchers of the legacy live account (cross-minute fires mint distinct clientOrderIds, and Schwab has no server-side idempotency: the rollback path would recreate the 08-18 twin-order class at N×).
   - `!book.enabled` → **NEW entries and rotation are skipped; protective exits, `freeStaleSells`, and reconcile KEEP RUNNING while the book has open positions or non-terminal orders.** A blanket skip is a one-click route into the documented nightmare state — a funded live book with no protective exits (`:1396-1408`). Disable means "stop adding risk," never "abandon the book."
   `runAutopilot` (`:1110`) takes the book. `capAccount` (`:1096`) for `kind='live'` uses `LEAST(env TRADING_CAPITAL_CAP_USD, book.capital_cap_usd)` — nulls fall through; the env cap remains a fleet-wide floor. `sizingPrice`/fail-closed reads unchanged (`:526`, `:1127-1139`). **The drawdown breaker goes fail-closed in PR1:** both call sites currently wrap `evaluateEquityGuard` in `.catch(() => null)` and treat null as not-halted (`:1195/:1310`) — any error the re-key could introduce would silently DISARM the breaker; a guard-evaluation failure now halts NEW entries for that fire (exits unaffected, mirroring the `:1127-1139` read doctrine). The flag is read **per-fire** via `multiAccountEnabled()` — never a module constant (module consts are invisible to guards; `:81` hazard class).
6. **Idempotency-key text** (`:247`): `requestId = \`auto-${book.ref}-${minute}-${SYM}-${side}\``. Legacy refs are `'paper'`/`'live'` → **byte-identical strings today**, no flag branch, no cross-deploy retry hazard. Same rule for the reconcile-ledger `decision_id` derivation (D2 #2). Swing's book-less `requestId` is acceptable because swing stays pinned to one book (below).
7. **Schedules:** per-book schedules for the main autopilot leg, minted flag-on by the store autopilot route: `taskType = trading-autopilot:{sub}:{book.ref}`, `taskData {userSub, mode: book.kind, bookId, universe}`, queue `intelligent-trades`. ## Migration & live-safety plan

**Invariant: the live book trades every market morning. Every core deploy in this plan ships via `scripts/oshal-deploy.sh` (auto-rollback) in a market-closed window (after 16:00 ET or weekend), kernel first, then the store package via `docker cp → deployed-apps + api restart`.**

1. **Backfill (PR1, both rails):** ordered statements — add columns → mint legacy books (deterministic ids, `ON CONFLICT (book_id) DO NOTHING`) → **install the D2.3 trigger** → backfill `book_id` (`WHERE book_id IS NULL`, re-run no-ops) → create book-scoped unique indexes. **Trigger BEFORE backfill is load-bearing:** writers do not stop for a market-closed window (`reconcileOpenOrders` fires every 5 minutes even when closed — `trading-schedule-dispatch.ts:1389-1393` — the paper book trades extended hours, and un-redeployed store-twin code inserts book-less rows until its own `docker cp`). An insert landing between a backfill-first UPDATE and a later trigger install would stay `book_id NULL` forever, and a NULL never conflicts in the book-scoped unique index — silently escaping the twin-order arbiter. Trigger-first catches every concurrent insert; the subsequent backfill sweeps everything earlier. HWM/peaks/daily-equity rows are **re-keyed in place, values untouched** — the breaker state and trailing peaks carry over exactly.
2. **Coexisting indexes:** old mode-scoped unique indexes/PKs are retained through PR1–PR3. Safe because under the bijection any old-index violation is also a new-index conflict, which the new `ON CONFLICT` target absorbs first; and old code rolled back by `oshal-deploy.sh` still finds its `ON CONFLICT (user_sub, mode, …)` indexes. The only atomic swap is the config-overrides one-active index (PR2), whose clone-backfill keeps a rollback benign (identical rows).
3. **Flag stays false through PR1–PR3.** Verification after each deploy-morning: `/api/trading/ledger` vs Schwab `/transactions` parity (venue is truth), `oshal_trading_equity_hwm` values byte-unchanged, watchdog heartbeat id present, logs grepped for `unique_violation`/`duplicate_submission` anomalies.
4. **Cutover (PR4):** the precondition script refuses unless: discovery has run and every **enabled** live book has `account_id NOT NULL`; `SELECT count(*) WHERE book_id IS NULL` is **0** on orders/signals/decisions and the five side-stores (predictions' deliberate NULL-user rows exempt); and — asserted via `pg_constraint` — the mode-PK swaps have landed on all five side-stores **before any non-legacy live book may be set `enabled=true`** (the book-enable route itself refuses while a legacy mode-PK still exists on the HWM table, because a second live book's HWM insert against the old PK raises `unique_violation`, and a pre-PR1 `.catch(() => null)` would have read that as not-halted — the breaker failing OPEN). Then: flag default true; **schedule ADOPTION, never blind creation** — the autopilot route lists the user's existing `trading-autopilot` schedules and adopts them **by id** (updating `taskData.bookId` in place via the schedule store), minting new schedules only for books that have none, and explicitly adopting-or-deleting the legacy book-less paper leg (`ScheduleService.resolveCreateTarget` forks a `--<sha24>` twin id on any ownerSub/taskType mismatch — a blind re-POST double-fires the real account, and the watchdog's substring grep matches both ids so it cannot see it); post-mint, an invariant assertion (and a watchdog check) proves **exactly one active autopilot schedule per (user, book)**, alerting on more. After the NULL-count precondition passes, `book_id` goes **`NOT NULL`** on orders/signals/decisions + the five side-stores — the trigger and mode indexes are then dropped with a straggler writer failing LOUDLY instead of minting an unarbitered row (the cutover spec inserts a legacy-shaped book-less order row and asserts it is REJECTED). PK swaps via guarded DO-blocks (`pg_constraint` existence checks); drop the legacy mode unique indexes (065-successor migration) and the D2.3 trigger; retire `SCHWAB_ACCOUNT_NUMBER` from compose/`.env.example`; reconcile collateral (README/ROADMAP/ADR index/counts generator) in the same change.
5. **Rollback:** PR1–PR3 → previous image (safe per §2). PR4 → set `TRADING_MULTI_ACCOUNT=false`: legacy books continue on the book-scoped indexes, and per-book schedules **hard-skip as logged no-ops** (D3.5 — they must never fall back to the legacy live book, which would make N schedules trade the one real account with cross-minute duplicate orders Schwab cannot dedupe); the disarm runbook deletes the per-book legs. **Once any non-legacy live book has a ledger row, the doctrine is flag-off + roll-forward ONLY**: re-creating the mode unique index fails on any cross-book collision, and while it is absent a pre-PR1 image's reservation `ON CONFLICT (user_sub, mode, client_order_id)` errors on EVERY submission — protective exits included, i.e. that "rollback" takes the live book unprotected. The PR4 precondition script stamps a deploy marker that `oshal-deploy.sh` checks to refuse auto-rollback past the PR1 image boundary, and the cutover spec rehearses the reverse SQL against a two-live-book dataset so its failure mode is known before an incident, not during one.
